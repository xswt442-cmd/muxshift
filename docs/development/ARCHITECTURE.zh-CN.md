# 工程架构

[English](ARCHITECTURE.en.md)

当前仓库是一个可运行的早期原型，不是一个成品应用。已实现：Go Core 的会话配置模型与事件时间轴、从 HLS 播放列表读取轨道与时间信息、有界的直播回看缓冲与录像切割，以及三个客户端——用 MyGo 原生播放的桌面端、用 hls.js 在浏览器里播放的 Web 端、把用户点选的地址交给本机会话的浏览器扩展。桌面端在同一个会话里登记多个媒体源，由场景决定显示哪路画面、听见哪路声音；它支持手动对轴、运行时导入源（导入后能出画）、把缓冲切成录像并在会话窗口里播放与跳转、持久化设置与 100%–200% 缩放下的折页。尚未实现：媒体采集、混音、跨源自动同步、受控多路播放，以及把回看窗口当作可 Seek 的授权区间（P16.4 阻塞中）；浏览器扩展的工具栏真实点击仍未验收。

## 模块及边界

| 目录 | 当前状态 | 职责边界 |
| --- | --- | --- |
| `core/` | 会话配置模型 | 共享的媒体会话配置与控制契约所在位置 |
| `core/hls/` | HLS 元信息读取 | 读播放列表、轨道与首个样本时间，不转码、不对外供流 |
| `desktop/` | MyGo 桌面实验应用 | 把多个媒体源登记进一个 Core 会话，按场景显示画面与听见声音，并管理播放器生命周期；不承载共享业务逻辑 |
| `web/` | Web 客户端（hls.js 与 MSE） | 只监听本机的会话服务与静态页面；播放能力受浏览器限制，不假装等同桌面 |
| `extension/` | 浏览器扩展与本机 Host | 把用户点击后选中的那一个页面地址交给正在运行的会话；不复制 Cookie、请求头或密钥 |
| `tools/separate/` | 实验脚本 | 用自带权重把一段录音分成人声与非人声两份 WAV；不在播放路径上，模型权重不随仓库发布 |
| `design/`、`tools/designtokens/` | 设计 token 与生成器 | 颜色、圆角、间距、字号只在 `design/tokens.json` 定义，生成 `web/tokens.css` 与 `desktop/tokens.go`；两端只消费生成物 |
| `testplace/` | 本地忽略目录 | 实验、临时记录、Agent 工作文件 |

客户端与 Core 的预期依赖方向为 `desktop → core ← web`；浏览器扩展通过显式协议衔接，不直接耦合桌面 UI。这里描述的是模块所有权约束，不代表这些调用已经实现。

## Core 会话模型

`core.Session` 只保存配置，不保存播放状态。一个会话持有它读取的媒体源、源中发现的音视频与字幕轨、把多条轨绑到同一参考轨的同步组、决定显示什么与听见什么的场景，以及把场景交给某个能力的输出。每条轨最多属于一个同步组。每次操作要么完整生效，要么不改动会话；被拒绝的操作不记录事件；删除媒体源会同时删除它的轨以及对这些轨的全部引用。

## Core 事件时间轴

`core.Timeline` 用 `targetMediaTime = sharedEventTime + mappedOffset` 把同一个共同事件时间映射到各条轨的媒体时间。偏移为正表示该轨的媒体时钟走在前，按直播跟随需要把它延后同样的时长；偏移为负表示该轨还没到达当前事件的内容。设置偏移是替换而不是叠加，因此同一校准结果应用两次不会累积。没有偏移的轨按 `not_aligned` 报告，不会被放到猜测的时间上。

`core.Playhead` 是共同事件时钟：从零开始且处于暂停，只有播放时才前进；跳转保留当前暂停或播放状态。暂停、恢复与跳转一起移动这个时钟和每一条轨的目标时间，从不改动已存的偏移。`Timeline.AdjustShift` 在已存偏移上加减一个步长并返回新偏移，用「从当前偏移出发」的方式保证连续按十次 0.1 秒就是 1 秒；溢出时返回 `core.ErrTimeRange` 并保留原偏移。这两个类型都不解码媒体、不操作播放器、不访问网络。

## HLS 元信息读取

`core/hls` 只做两件事：读一个 HLS 播放列表的描述，以及读出它包含的音视频轨与每条轨的首个样本时间。它用 `gohlslib` 解析播放列表与分片，不手写 parser，也不下载多余分片。`Read` 只接受媒体播放列表，主播放列表由调用方选择变体；`Probe` 接受主播放列表，由库选择默认变体。

轨道的 PTS 只在同一条流内有意义：库会把时间戳归一化到该流的首个样本。`EXT-X-PROGRAM-DATE-TIME` 声明的墙钟时间能建立候选的跨流时间参考，但两个不同直播源里相同的墙钟时间不保证对应同一个比赛事件：导播、转码与缓冲都会改变内容与时间的关系。因此 `Align` 给出的是候选偏移，不宣称完成内容级对齐。缺少该声明时返回 `core.ErrNotAligned`，不猜一个精确匹配。`Attach` 把流建成 Core 的媒体源与轨，失败时回滚到调用前的状态；`Apply` 校验后再把偏移写入 `core.Timeline`。

地址只接受 http 与 https，拒绝带凭据的 URL；从公网地址发起的重定向不允许落到本机或内网地址。超时、取消与非 200 响应都以可判别的错误返回，不会把明文凭据写入日志。

## 桌面适配（MyGo）

`desktop/` 是一个 MyGo 实验应用，它把命令行给出的每个本地文件或 http(s) 地址登记成一个 Core 媒体源：网络来源先用 `core/hls` 读出真实轨道再登记，本地文件登记成一条视频轨与一条音频轨（MyGo 不枚举本地文件的轨道）。会话里有一个场景和一个桌面窗口输出，场景决定显示哪条视频轨、听见哪条音频轨以及各自的音量与静音；界面上的按钮只改场景，`apply()` 再按场景设置每个播放器的显示、静音与音量。

一个媒体源对应一个播放器实例，这是桌面适配当前的实现策略，不是 Core 的约束：Core 只描述媒体源、轨与场景。未被场景选中的视频不是从视图里删除，而是保持播放器存活并隐藏。

窗口的壳层是一个工作台：顶部全局条、左侧 rail、中间舞台与控制、右侧 inspector、底部时间线 dock、底部状态条。舞台/来源/诊断/设置/混音五页在 rail 上；inspector 有选中源时显示该源的可操作详情（显示、听音、音量、±0.1s、试对轴、重试、移除），没有选中时显示只读的会话摘要；dock 显示共享事件时间与每源偏移（P16 前只读）。rail 收起时顶部条会多出一个页面按钮，写着当前页与下一页，所以最小窗口下这些页仍然可达（P18.1）；rail、inspector 与 dock 按客户区尺寸自动收起（<900px 收 rail、<1160px 收 inspector、<660px 高收 dock），每个都能手动开关且手动选择优先。诊断页报告本次运行打开的回放缓冲区（P18.3-b）：每个缓冲区的缓存分片数与字节数、录像数量与占用、系统不让删除的文件数、缓冲区实例的短名，加载设置允许的上限另起一行、写明它是上限而不是用量。它唯一的动作「忘掉没人播放的录像」让每个缓冲区删掉没有任何租约持有的录像：播放器打开着的录像不动，页面会写明哪个文件留下了以及原因；一次清理报告释放的字节是清理前后实测的差值，所以系统仍占着的文件绝不会被算成已释放。设置页（P15.3）还可以让窗口按离开时的样子回来（P18.1）：打开后，关闭时写入窗口框、页面与三个面板的开合选择，下次启动在第一帧之前恢复；没有任何显示器能显示的框会回到主显示器，页面或面板名是这一版不认识的，则整条记忆被拒绝而不是猜一个。设置页（P15.3）集中七个可持久化选项：起始页、新源默认音量、对轴步长、未对齐源是否静音、主音量、dock 默认开合与紧凑间距；应用时先校验再原子写入配置文件，取消不动已应用的值，重置只改草稿。DVR 分区（P18.2）编辑回放缓冲区的三个上限——保留多久、分片缓存上限、录制上限——并写出当前生效的值、产生它的规则（显式命令行参数、设置文件、内置默认）以及「零字节上限是取消该上限而不是缩小它」的提醒；快捷键分区如实列出窗口真正绑定的键。DVR 的三个数字把名字放在自己一行、控件放在下一行，因为在最小窗口上把 260px 的标签与三个控件排成一行会把行尾切掉（尺寸由 `testplace/p18/edgeclick -fit` 在 686×522 的内容区上量过）。来源导入在后台读取并提供「已读多少秒 + 取消」，失败只写一条错误通知（顶栏可点进诊断页、状态条可 dismiss）而不会留下半张源卡片；Ctrl+S/H/R 与 Ctrl+1..5 是窗口级快捷键（设置页如实列出），未选中源时按键会明说需要先选源；文本框持有键盘焦点时这些键一律不注册（P18.1），所以输入地址时既不会显示源、也不会跳页。界面上的每个动作都经过 `desktop/controller.go` 的单一入口，命令带上源标识与播放器代次，结果写入日志并回读一份快照，因此按钮的效果与日志、快照描述的是同一件事。设置页的来源分区（P18.2）记住人手添加的源的声音：默认关闭，打开后一个地址按**规范化之后**的身份保存——scheme 与 host 转小写、去掉默认端口、路径原样保留（把 `/a//b` 折成 `/a/b` 会把一个源的音量交给另一个源）；带凭据、query、fragment 或本程序打不开的 scheme 的地址是拒绝而不是删掉凭据冒充干净身份，本地路径只记绝对路径。用 `-media` 给的源不写回记忆，记忆值在场景第一次应用音频状态之前装上，记忆里的「不静音」也不会绕过未对齐保护。记忆的电平会写进场景自己的电平并交给播放器，卡片与输出因此一致，而不只是卡片知道；一次改动别的字段的 Apply 会保留草稿打开之后记住的地址，除非草稿按了 Forget；读不到配置文件的启动不写任何记忆，和它不写工作区是同一条规则。

P13.3 还验证了在同一窗口里把网页当成控制面：窗口上半是原生视频元素，下半是 MyGo 的 WebView，页面通过 `mygo.call` 调用 `Panel.Show` 等绑定方法，这些方法同样落到上面的命令入口。实测可行，但有明确代价：前端与绑定必须在 `mygo.App.Run` 之前注册，页面拿到的字段名取决于绑定值的小写 JSON 标签，网页尺寸不会自动匹配元素，并且 `CapturePage` 截不到 WebView（系统视图在自绘内容之下）。因此壳层的决定是采用「原生画面 + 可选网页控制面」，网页只能是命令与快照的消费者，原生路径始终是可运行的回退。


播放器的创建、显示、停止显示与关闭由同一个组件按顺序处理：关闭时在同一主线程回调里把来源标记为不显示并让指针失效，等窗口真的建出三帧，再在主线程调用 `Close()`；唤醒首帧的异步任务带实例代次，代次不符立即退出。重新打开同一来源采用交接式顺序：先打开新播放器，旧的继续绘制，等新的就绪后再关闭旧的，因为此构建在两个视频元素之间出现空档时新播放器不会拿到首帧。

交接有明确失败边界：新播放器在超时内没有画面时，旧播放器继续绘制并继续播放，被关掉的是没起来的新播放器，来源行报告原因；一旦新播放器有画面，旧的才释放。每次交接都绑定实例代次，连续快速点重新加载时只有最后一轮拥有该来源，交接对象随代次转移，所以同一播放器不会被关两次，旧回调也不会错误关掉新播放器。

此构建的 `ui/video` 有几处缺口，应用层做了补偿并如实记录：网络来源自己不交付首帧，需要一次向前的跳转（只在打开阶段补偿一次，跳转后的位置从播放器重新读取，不用假设值；补偿失败就保持未就绪状态并把实际错误显示出来，后台不会反复改动播放位置）；同一窗口里有两个视频或视频还没交付帧时 `CapturePage` 会读到空缓冲区并 panic，截图因此包了 `recover`；从未显示过的播放器位置不推进，所以「A 画面 + B 声音」要等 B 至少显示过一次；把界面上正在显示的视频元素换掉会让窗口停止重绘，因此所有播放器的视频元素始终在树上，只切换显示状态。

声音不靠听感判断：`IAudioMeterInformation` 只读采样默认输出设备的峰值，播放时有电平、静音后为 0、两路同时出声时电平更高。它不能区分是哪个进程在发声，因此每个采样窗口只运行被观测的应用并对齐时间。

手动对轴在 `desktop/sync.go`：`Timeline` 保存每条轨的偏移，`Playhead` 保存共同事件时间。暂停与恢复按会话里**一个显式的 Core 同步组**下发：第一次同步命令（暂停、恢复、锚定或微调）时，用当时场景选中的源建出这个组并固定成员，之后改变场景不会改变成员；组外的源继续播放，失败成员按源名上报。这样安排是因为一个场景以后可能同时显示两场互不相关的比赛、各自有同步组，按场景判断会把两场一起暂停。对某一源按 ±0.1 秒时，先把该源的偏移加减一步，再按 `事件时间 + 偏移` 定位播放器；目标早于流起点时拒绝并说明原因，不改另一路的速度。锚定把参考播放器的当前位置作为事件时间，因此重复锚定不会让目标漂移。未在时间轴上定位过的源默认静音，界面上的例外按钮可以放开或撤回——这是防剧透的可见、可恢复路径。

播放器报告的 `Position()` 是各条流自己的时间，不是内容时间：两条流的起点不同，同一位置上的内容也不同。跨源比较必须用内容标记（例如画面内嵌时码），实测剩余误差约 0.1 秒，来自 seek 落点与位置回报。

P14 把引擎细节收进一层适配：`desktop/player.go` 只暴露受控播放器需要的操作（播放、暂停、跳转、音量、静音、关闭）和一份只读状态（就绪、播放中、缓冲、位置、时长、错误），绘制、交接与唤醒仍走原始播放器；这样换引擎不需要改动会话与命令层。时间基准固定在 `desktop/timebase.go`：`media = event + offset`，两侧换算都拒绝负值与溢出。基线矩阵（一、二、四路以及直播+文件）由 `desktop/matrix_scenario.go` 采集就绪时间、位置推进、暂停冻结与切画面/听音，同时采 CPU、工作集与 GPU：四路时 CPU 峰值 9.66 秒/采样窗口、工作集 291 MB、GPU 25%，位置不再推进或暂停冻结都算失败。生命周期场景覆盖三次快速重载、运行中增删源、打不开的地址与关闭到零：重载只有最后一轮拥有源，移除后窗口与会话一致，运行中新增的 HLS 源可以就绪，而不可达地址是静默失败（`ready=false`、`err=nil`），界面只能如实显示未就绪，不能编造原因。引擎替换的结论是保留 MyGo（pin 在 `5a2f9c6`，MIT）：没有一项缺口造成验收失败，替代方案（libmpv、FFmpeg 自写渲染、WebView）都要先付许可、分发或集成代价；只有在需要 PCM 出口、每源多音轨、亚 100 ms 双源控制或非 Windows 客户端时才开一个有时限的试作，触发条件与证据见 P14 的引擎决策记录。

回看窗口在 `core/dvr` 与 `desktop/dvr.go`。`core/dvr` 把一个源的分片按序号存成文件：不是传输流的分片被拒绝，序列号跳号或下载失败时留下一条缺口而不是抹掉，两端都有节目时间时用它们量出缺口长度，并对外报告真实连续的可用区间。`Retention` 与 `MaxBytes` 限制目录大小，`Evict` 只删除未被保护的最旧分片，`Close` 删除文件与它自己创建的目录。`Join(from)` 把 `from` 所在的那段连续区间按顺序拼成缓存目录里一个新的传输流文件，落在分片中间的开始时间从该分片首帧起，跨缺口就拒绝，所以得到的文件本身可以播放；每次调用都发布一个新文件，已发布的录制不原地覆盖，因此播放器已经打开的录制不会被换掉，`Close` 会把缓冲区发布过的录制连同分片一起删除。`Record(from)` 做同一次拼接并额外返回一个 `Recording`：唯一 id 与文件名、请求的缓冲时间、文件真实首末帧的缓冲时间、首末媒体序号、当时的有效区间与缺口、源标识，以及文件大小与生成时间。字节先写到临时的 `.<id>.part`，写全并关闭后才改名，因此失败的切割只清理自己的临时文件，不会损坏更早的录制。`Recording.BufferTime(position)` 即 `position + StartBufferTime`，走的是缓冲区自己的时钟（从它存下第一段起算），不是源媒体时钟；要换算到源媒体时间必须提供实测的 `Anchor{Source, BufferStart, MediaStart}`，缺锚点或锚点属于别的源时 `SourceMediaTime(position, anchor)` 以 `ErrNoAnchor` 明确拒绝，而不是默认缓冲从零开始。`EventTime(position, anchor, offset)` 先把文件内位置加上 `StartBufferTime`，用 `Anchor.ContentTime` 落到内容时钟（缓冲时间就是 Core 时间轴持有的内容时钟），再减去已确认的轨道偏移；`SourceMediaTime` 保留为显式的容器域换算，用于按时间戳打开文件。`Valid()` 报告文件是否仍以该大小存在。请求时间不是文件首帧：只有请求正好落在分片边界时两者才相等。已发布的录制在消费者持有时不会被收回：`Lease(id)` 交出一份引用，桌面端在播放器打开文件时取走、在播放器真正关闭后归还，因此 `Release` 与 `Close` 只删除没人持有的录制，Windows 仍占用而删不掉的文件通过 `PendingCleanup` 如实报告，而不是当作已删除。录制预算（`Options.RecordingBytes`）与分片预算分开：一次切割先丢掉最旧且没人持有的录制，若剩下的全被租用就以 `ErrNoSpace` 拒绝，绝不为腾地方删掉播放器正在读的文件。`lease` 场景把这条规则端到端跑了一遍：5 MiB 预算下租用一份快照后，随后三次切割每次都丢掉一份未被租用的快照，租用文件始终有效、在 `Close` 删掉全部分片后仍能解码，直到消费者关闭并归还租约才消失（`testplace/evidence/P16/ownership.md`）。`-dvr-recording-bytes` 设置这个预算（默认 256 MiB，0 表示不限），桌面端每个播放器实例各持一份租约。

把一个源切到录像是一次事务（`desktop/replay_swap.go`），不是改地址：切割与取租约在同一把缓冲区锁内完成（`RecordAndLease`），替换播放器在绘制线程打开，只有它真的出画之后才提交——提交在同一个主线程步骤里换掉 item 的播放器、录制与租约，旧播放器先关闭、旧租约后归还。播放器打不开文件、永远不出画、或这次切换被更新的切换取代，三种情况都会关掉替换播放器、归还它的租约，并保留 item 原有的画面与租约。item 的地址与 Core 源全程不变，正在播的录像另外记在旁边，所以窗口与日志可以写「这是源 1 的历史」而不是假装源换了地址。切换还没结算就把这个源关掉时，替换品由 `sync.Once` 收尾一次——关闭与迟到的回滚不可能把同一份租约各还一次；显示中的录像播放器即使进 `pending` 暂停等别的播放器接手，租约也留到它真正 `Close()` 之后才归还。缓冲区只为自己那个源切割，不在场景里的源其替换品始终隐藏，所以后台切换不会抢画面。`swap` 场景覆盖六条切换路径，租约计数或舞台上的录制不对就让这次运行失败，并把「租约为零」与「播放器已关」分成两条断言；`swap-two` 覆盖别人的缓冲区与后台切换（`testplace/evidence/P16/swap.md`）。

三种身份彼此分开、绝不互相替代。`PlayerGeneration` 指 item 内一个播放器的一生，切换替换播放器时递增。`SourceMediaEpoch` 指源媒体时钟的一段连续运行：`Buffer.Epoch()` 从 `Options.SourceEpoch`（或 1）起算，遇到播放列表里的 `EXT-X-DISCONTINUITY` 就前移，因此在跳变之前切出的录制仍保留当时的 epoch。`BufferInstance` 指一个 DVR 缓冲区：`Buffer.Instance()` 在创建时固定，所以同一个源的两个缓冲区各有一份时钟，尽管它们的录制写着同一个源。`RecordAndLease` 把实例与 epoch 一并写进 `Recording`，`Anchor` 则声明同样三件事以及自己实测时的连续区间。`SourceMediaTime` 只有在锚点确实实测过（`MeasuredAt` 非零）、与录制同源、来自同一个缓冲区实例、属于同一个 epoch，且声明的区间包含被换算的缓冲时间时才返回结果，否则以 `ErrNoAnchor` 明确拒绝。因此一次回放切换只递增播放器代次：`swap` 场景会打印 `buffer buf-… epoch 1 -> buf-… epoch 1, generation 1 -> 2`，三者中任何一个变化都会让这次运行失败（`testplace/evidence/P16/epoch.md`）。

锚点是**量出来的**，不是从源标识推出来的：`desktop/replay_clock.go` 用 ffprobe 读录制文件首帧的容器时间戳，把 `Recording.StartBufferTime` 与这个媒体时间配成一对实测值，`Interval` 覆盖该录制；测量在缓冲区存下第一段之后就在后台进行，从不跑在绘制线程上。锚点描述的是「哪个分片」而不是「什么时候测过」：`Buffer.CurrentSegment()` 在一次加锁里给出被测量分片与它所属的 epoch 和实例，跳变之后测的是新时钟；测量失败不会被永久缓存，但重试的触发条件是**缓冲区又存下了一段新分片**（`Buffer.NewestSegment()`），不是每次轮询，已经成功的锚点也不会因为区间增长而重测。同一个分片连续两次读不出来时，改为测量当前最新的分片，并用它自己的缓冲起点建立锚点，于是它之前的窗口继续被拒绝，而不是倒推。换算按 `B = R + StartBufferTime`、`C = B`（内容时间就是缓冲时间，从缓冲存下的第一段起算）、`E = C − 该轨已确认偏移` 进行，容器换算 `M = Anchor.MediaStart + (B − Anchor.BufferStart)` 只用于把位置落到文件里，并且逐项拒绝：锚点未测量、源或缓冲区实例不同、epoch 已经前移、窗口早于被测量的那个分片、窗口不在同一段连续区间里（`Buffer.RangeContaining` 在一次加锁中判断整段窗口是否落在一条区间内：同一 epoch 内跳过分片同样会截断区间，此时不能凭同一个锚点跨越）、轨道在 Core 时间轴上没有已确认的偏移（零偏移合法，但必须确认过）。`commonReplay` 因此不再把缓冲时间当成媒体时间：它先把每路 `Available()` 的起点换算成媒体时间，再按窗口长度推出终点——同一 epoch 内缓冲时间与媒体时间一起走，只有起点是实测样本。`hls-vod` 的一次 `swap` 实测里，缓冲 0s 处的媒体时间是 `1.466667s`，说明这两个时钟本来就不一样；`live-a`/`live-b` 跑 `dvr` 时两路的容器 PTS 基准相差约 52 秒，换算后如实报告「不重叠」，而不是像按缓冲时间相减那样把它们当成同一段（`testplace/evidence/P16/anchor.md`）。正例用的是同一事件的两份播放列表：第二份是同一批编码帧、每个容器时间戳晚 4 秒，ffprobe 与逐帧哈希各自证实这一点，而画面相同意味着内容偏移是 0。`common` 场景给两路都确认零偏移，得到窗口 `0s..30s`，锚点报告的容器起点仍相差 1.47s 与 5.47s；反过来把这 4 秒容器差写进轨道偏移，窗口就缩成 `0s..26s`——这正是它不能变成偏移的原因，去掉确认则 `commonReplay` 以 `ErrNotAligned` 拒绝（`testplace/evidence/P16/common.md`）。同一次实跑也暴露两个时钟并不是同一个时钟：播放器的 seek 与 `Position()` 跟的是文件自身从首帧起算的呈现时间，锚点量的却是容器时间戳，遇到带 mux delay 的素材两者相差正好是那个 delay——这正是事件时间要建在内容时钟上、容器换算只用于打开文件的原因。共同窗口现在是内容时钟上的候选交集，但仍然不是已授权的 Seek 区间：播放器位置落位不等于目标帧已呈现。转换本身放在 `desktop/replay_clock.go` 里的一个小 `mediaClock`：它由锚点量出，`Player(container)` 减去文件首帧的容器时间戳，`Container(player)` 再加回去，`playerWindow` 把缓冲窗口映射成播放器能 Seek 的位置（在缓冲起点切出的文件从 `anchor.BufferStart` 开始播）。两份只有时间戳相差 4 秒、画面完全相同的文件，转换后播放器窗口都是 `0s..30s`——平移留在转换层，不会变成轨道偏移（`testplace/evidence/P16/clock.md`）。


录制文件的时间轴是缓冲区自己的时钟，从它存下第一段起算，所以文件内位置 `p` 对应缓冲时间 `StartBufferTime + p`，`StartBufferTime` 是首帧的缓冲时间，通常比请求早不到一个分片。这个时钟不是源媒体时钟：缓冲区可能中途加入直播流，因此只有拿**为这个源实例实测过的** `Anchor` 才能把录制放回源时钟，缺锚点或锚点属于别的源一律拒绝，而不是默认从零开始；再回到共同事件时间时减去已确认的该轨偏移。`contract` 场景用带烧录时码的源验证这一点：请求 3 秒得到从 2 秒开始的文件，首帧时码 `00:00:02.000`，文件内 1 秒处时码 `00:00:03.000`，正是请求的那个时间；第二次切割不会损坏第一份文件（`testplace/evidence/P16/contract.md`）。

桌面端每秒读一次直播源的播放列表写进这样的缓冲区，读取与画面无关：暂停输出不会暂停输入，这一点由 P8 实测记录。两路缓冲按与时间轴相同的偏移规则把各自的 `Available()` 换算到共同事件时间再求交集；没有已知偏移时返回错误而不是猜测，区间不重叠时如实报告而不是悄悄丢掉一路。

把录制放进正在运行的会话，现在有两种用法都成立。录制可以在会话启动时登记成源、再由场景切过去；运行中导入的源同样能打开并出画——播放器在绘制线程创建，一旦报告 ready，舞台就画它、位置继续推进。`replay` 场景测了四种打开方式（启动时登记、先隐藏再切过去、运行中导入、在已有卡片上重开），四种都 `ready=true`，画面里的烧录时码与位置相符；`sources` 场景在运行中导入一个本地文件，读到 `ready=true`、`picture=[track-5]`。`Join` 产出的文件作为唯一源、在单独启动的进程里打开时同样会播放，`desktop` 的 `-replay` 模式就是这种用法。

早先「运行中新建或重开的卡片出不了画面」的结论已撤回。它的原因是应用层缺陷——播放器原先在不绘制窗口的 goroutine 里创建，live HLS 因此没有首帧、跳转后停在跳转点；改为在绘制线程创建后，直播播放列表与录制文件都能正常出画。修复前做过的隔离实验（`testplace/poc/twowin`）仍然成立：障碍从来不在录制文件或窗口本身。先前试过的本机 HTTP 出口因为没有任何改善已经删除。

缓存里的分片只做了结构检查：长度是 188 字节的整数倍、每个包的首字节是同步字节，并且拒绝无法读取或不是传输流的内容；这不能保证每一帧都能解码。因此现在的准确说法是「有限 HLS 分片缓存、基于已缓存分片的连续区间查询与录制拼接」，录制文件的播放只在 Windows 上以 MyGo 单源方式验证过。

### 回放时钟契约（P16.3d 进行中）

三个时间域必须分开命名，任何一个都不能冒充另一个：

| 时间域 | 谁产生 | 用途与规则 |
| --- | --- | --- |
| `ContainerPTS` | ffprobe 读出的容器时间戳（含 mux delay） | 只作取证与识别基准；也用于把文件位置交给播放器（`MediaTime`/`playerWindow`），但**不能**当作 Core 的媒体时间 |
| `ContentTime`（缓冲时间） | DVR 缓冲自己的时钟，从它存下的第一个分片起算 | 就是 Core 时间轴使用的媒体时间：`commonReplay`、`Recording.EventTime` 与 `replayEventTime` 都建立在它上面 |
| `EventTime` | Core 时间轴 | `ContentTime` 减去该轨**已确认**的偏移；零偏移合法，未确认的零偏移不合法 |

换算与拒绝：

- `B = R + StartBufferTime`（文件内位置 → 缓冲时间），`E = B − 已确认偏移`（事件时间）。容器时间不进入这条链路。
- 打开播放器需要另一条换算：`M = Anchor.MediaStart + (B − Anchor.BufferStart)`（容器时间），再经 `playerWindow` 换算成播放器窗口。
- 锚点必须实测（`MeasuredAt` 非零），且与录制同源、同缓冲区实例、同 epoch，并声明覆盖被换算位置的连续区间；任一条不满足就返回 `ErrNoAnchor`，不做外推。
- 一个文件内的位置 `p` 是**文件内位置**，不是缓冲时间；`Recording.EventTime` 自己会加 `StartBufferTime`，调用方不要再加一次。反向换算用 `replayPosition`。
- 同内容、仅容器时间戳平移的两份文件换算到事件时间后相等（实测：容器差 4 秒的两路在内容 6s 处都是事件 6s），平移只能留在文件位置换算里，不能变成轨道偏移；给第二路填 4 秒 `TrackOffset` 会篡改产品里的内容同步语义。
- 共同窗口目前是候选交集：它是内容时间域上的交集，但「`Position()` 落位 = 目标帧已呈现」仍不成立（连续播放有每文件约 35ms / 720ms 的有界滞后），因此要等 P16.4 的授权契约才能当作可 Seek 区间。

### 回看授权的契约（P16.4a）

`core/dvr` 的 `PlanSeek` 把一次回看请求变成一个不可变的 `SeekPlan`：目标事件时间（私有字段，只通过 `Event()` 读取）、每一路要打开的录像与文件内位置，以及做出这个决定时的身份（源、缓冲区实例、epoch、播放器代次、录像 id）。缓冲区、锚点和录像的实例名都不能为空——三个空串互相相等，并不能证明它们来自同一个缓冲区。它只做判断，不打开播放器、不改场景、不动租约，因此可以完全用单元测试证明。

授权逐项检查，任何一条不成立都返回包住 `ErrNotAuthorized` 的错误，并指明哪一路、哪一条：

- 偏移必须**说过来源**（`Alignment{Basis}`）；只接受 `measured`、`manual`、`shared-start` 三个值，未定义的字符串与空 basis 一样拒绝——零偏移本身不算确认，两个中途加入的缓冲都报 `ContentTime=0s` 时，数字一样并不证明是同一帧。
- `event + offset` 不得溢出，内容时间也不能为负。
- 目标必须落在该路缓冲区持有的**那一条连续区间**内；缺口、跳过分片、已被淘汰的区间都拒绝，不做钳制。
- 锚点必须实测，且与录制同源、同缓冲区实例、同 epoch，时间还要落在锚点声明的区间里；**锚点的测量起点必须仍在当前这条连续区间内**，测量过的那段媒体被淘汰后，旧锚点不能再授权。
- 录像必须真的覆盖目标内容时间（`[StartBufferTime, EndBufferTime)`，右端点按半开区间拒绝），并且有可打开的**身份**（非空 id 与路径）。
- 文件内位置 = 内容时间 − `StartBufferTime`，所以缓冲中段切出的文件从 0 开始，而不是从请求时间开始。
- 计划绑定**播放器代次**：同一路换了播放器，即便源、实例、epoch 与录像都没变，旧计划也失效。

`SeekPlan.Matches` 在真正打开任何东西之前再比一次：它比较的是**整份身份快照**（源、缓冲实例、epoch、播放器代次、偏移与来源、连续区间、锚点的测量、录像身份），而不是投影出来的文件位置——换了锚点或换了播放器，位置可能一模一样，但那已经不是同一个决定。缓冲区重建、epoch 前移、换了一份录像、偏移被撤回或播放器被替换都会让旧计划失效，回答里写清是哪一路变了。`SeekPlan` 的分片是私有的，`Hops()` 只交出副本，计划生成后不能被外部改写。这一层只回答「逻辑上允许去哪」；位置是否落位、目标帧是否呈现属于 P16.4b/c，契约里不假装知道。

### 回看授权的适配层（P16.4b-1）

`desktop/replay_seek.go` 把**当前这次会话**读成 `PlanSeek` 需要的 `SeekSource`，再在提交前用同一份读法复核一次。它同样不打开文件、不切录像、不建租约、不碰播放器。

- 每一路的值都来自活状态：录像来自真正发布过的那一份 `Recording`，锚点来自该路已实测的锚点，偏移来自 `Timeline`，播放器代次来自 `item.generation`。没有任何字段有默认值。
- **偏移的来源，连同它建立在哪个缓冲区时钟上，都当真记录**：以某路为基准的对轴与 ±0.1 秒微调都写 `manual`，并记下当时该播放器正在读的缓冲实例与 epoch。`shared-start` 留给本版本并不执行的那项检查：把一路选作参考，并不证明两个缓冲区从同一内容帧开始，所以没有任何操作可以声称它。`SetShift` 只改数字，本身不够——「有偏移、没有来源」是首要的拒绝情形，因为零偏移和未确认看起来完全一样。
- **来源只属于那一个缓冲区**：内容时间从该缓冲区自己存下的第一段开始计时，所以针对旧缓冲的校准对同一路后来重建的缓冲区毫无意义，重新测量锚点也补不上。适配层一旦发现记录的实例或 epoch 与正在读的缓冲区不同就拒绝；只有把新缓冲区重新放到时间轴上，它才重新可用。
- **只有正在播放该缓冲区录像的播放器，才能记录身份**：实时播放器与 DVR 缓冲区并行存在，但没有任何东西证明它的位置就是这个缓冲区的内容时钟，所以直播播放期间的校准不记身份，也不能授权回看——拒绝时会说明这次偏移是在「没有在读这个缓冲区录像」的播放器上做的。录像播放器确实读的是缓冲区的时钟，但经过文件自己的零点，而文件的零点在缓冲区里从 `StartBufferTime` 开始：对轴写入的播放头位置与微调算出的目标都是内容位置，因此下发给播放器前要先换成文件位置，而校准记录则绑在这一份缓冲区上。
- **不凭空造录像**：一路可以有自己的缓冲，但只有已经切出来的 `Recording` 才算数；没有录像时如实报「没有可用于计划的录像」，不填假 id、也不先切一个文件来凑条件。
- **快照与复核之间不能拼接两个时刻**：缓冲区的实例、epoch 与连续区间在一次加锁里读出（`Buffer.State()`），随后再读一次并要求完全一致；不一致就报「读状态期间缓冲区变了」，而不是把两次读拼成一个看起来自洽的决定。测试钩子 `replaySnapshotHook` 放在两次读之间，单元测试用它移进一段 discontinuity 来证明拒绝真的发生。之后还要再问一次会话：`runners` 已经指向另一个缓冲区，或该 item 的源与代次变了，都要报「读状态期间缓冲区/播放器被替换」——否则旧缓冲区自始至终是稳定的，两次读会一致，却在描述会话已经不再播放的东西。
- 任何失败路径都只返回错误：播放器仍为空、没有新的待关闭项、缓冲实例与代次不变。`planReplaySeek` 只是把每一路的 `SeekSource` 交给 `PlanSeek`；`confirmReplaySeek` 重新取一遍快照后调用 `Matches`，失败时把 core 的理由原样带回。

### 把决定变成资源（P16.4b-2）

`desktop/replay_txn.go` 执行一次已获授权的决定。它复用既有的回放播放器生命周期——`recordAndHold` 一次调用里发布录像并取得租约，`measureRecordingAnchor` 去测量真正写出来的那个文件，`openReplayFile` 打开播放器——自己只加事务，不另造第二套播放器路径。

- **计划按真正切出的文件重建**，不沿用事务开始时的旧计划：每一路按 hop 的内容时间切割、测量新录像、再跑一次 `PlanSeek`；哪个 hop 的位置与文件真正开始的地方对不上，事务就在提交前结束。录像与它的租约出自同一次调用，所以只要文件存在，就有租约压着它。
- **在所有东西就绪之前，什么都不替换**：每个替换播放器都画在该源已有画面的下面（`stage` 通过 `pendingSeekPlayer` 找到它），因为从未被绘制的播放器不会产出第一帧，而事务要等它在与单源切换相同的交接预算内出画。出画之后才重新读会话（`revalidateSeekTxn`）：item 的代次、背后的 runner、校准绑定的缓冲身份，以及重建计划自己的 `Matches`，必须同时仍然成立。
- **提交是绘制线程上的一个步骤**：一次性替换每一路的录像、租约、锚点与播放器，并让代次加一。它依赖的一切都在**同一个步骤里、安装任何东西之前**复核：只要有一路已经变了，任何一路都不会被替换。旧播放器与旧租约在替换之后才关闭和归还，所以观看者不会看到空舞台；提交前任何一步失败，都会关掉它打开的东西、还掉它取的租约，并让各路保持原样。
- **提交并不等于播放器已经落到目标帧**：为目标切出的文件从分片边界开始，目标可能落在文件内几毫秒处；提交后播放器停在文件起点，日志会说明后续 seek 步骤还要走多远。让播放器去定位并确认位置是 P16.4b-3 的事，两步都不声称画面已确认。

### 把播放器落到目标位置（P16.4b-3）

`settleSeekTxn` 在同一个事务里跑：所有替换播放器都出画之后、任何东西提交之前。每个播放器先暂停，再被要求定位到目标在**自己文件里**的偏移（`step.offset`，即计划里的 hop 位置，不是文件起点），然后反复读取，直到它在就绪、非缓冲的情况下连续两次报告该位置（容差 `seekSettleTolerance`＝40 ms）。原本在播放的播放器在到达后从该位置继续播放。

- **始终到不了的播放器按普通失败回滚**：事务关掉它打开的东西、还掉租约，会话不会停在一个无法显示请求时刻的文件上。
- **事务证明的是位置，不是画面**：引擎只能报告播放器被要求去了哪里，没有可靠办法说明那个位置上的帧正在屏幕上；事务记录每个播放器**实际报告**的位置（连同请求值与两者残差），从不声称画面已确认。引擎报错按未到位处理；落在 40ms 容差内的播放器也未必真的移动过，所以日志写的是 `requested`、`reported`、`residual`，而不是把请求值重复一遍。

### 一个会话里的两种回看（P16.4b 交错）

单源切换（`playRecording`）与多源事务可以同时进行。两者不是共享会话，而是互相让位：事务在提交步骤里、安装任何东西之前，先确认自己仍是登记在案的事务；切换在替换播放器之前，先确认条目代次没有被改过。被抢先的切换关掉自己打开的播放器、恰好归还一次租约；被抢先的事务什么都不安装。

关闭会话时先中止仍在进行的事务，租约与播放器走的是与失败相同的回收路径。那里的两秒只是「该报告一次」的阈值，不是可以提前关掉的许可：准备任务可能还停在切割、ffprobe 或打开播放器里并仍在读那块缓冲，所以关闭会先记下已超过预算，再等准备任务返回，之后才关闭任何缓冲。这类等待也不能占用准备任务正在等的线程：窗口关闭会在绘制线程的关闭监听里停掉事务并等它返回，因此准备任务投递到绘制线程的每一步都是有界的（`seekDispatchWait`），到点就放弃等待——而且投递本身也放在事务自己的 goroutine 里，因为 `mygoRunOnMain` 会一直等到绘制线程执行回调才返回，把预算放在它返回之后等于没有预算；它投递的那一步在停止之后跑起来什么也不做，而且每一步都在「停止」所用的同一把锁下执行：停止要么等这一步把播放器调用做完，要么先到达、让无可调用。读取「是否已就绪」也一样算一步。每一步的结果由它自己的通道交回，而不是写进调用方的变量，因此超时返回的调用方不会与仍在运行的迟到回调共享内存。中止事务同时取消它启动的探测，关闭因此不必等一个已经无意义的 ffprobe。后台准备在打开播放器之后会再确认一次归属，若会话或更新的事务已经接手，就由它自己把播放器关掉；每笔事务在工作返回时给出信号，关闭会话等这个信号（有界，见 `seekShutdownWait`）之后才关闭这些文件来源的缓冲区。场景 `interleave` 在同一会话里跑两种先后顺序与关闭中止，并核对租约与代次（`testplace/evidence/P16/interleave.md`）。
### Mixer 页（P17.4a 第二步）

rail 上的 Mixer 页是覆盖层的界面：一行只读的输出设备（`system default (device switching unavailable)`）、覆盖层自身的摘要、`Mute everything`，以及每个源一行——自己的静音、Solo 开关、排他的 `Hear`、音量滑杆。每行末尾是该源与窗口其他部分同源的说法：被听到，或安静并列出全部理由。场景本身也可能持有静音（来自另一处界面或恢复的布局），播放器会照它静音，因此这一行把场景的静音也列为一条理由，绝不把这样的源说成被听到，同时不改动那条静音。

页面不假装拥有本版本没有的能力：共享 PCM 总线、ducking、平移、每源 EQ、切换输出设备与电平表在底部如实标注为不可用，且不提供任何控件。

改变电平不是路由。场景里没有的源，滑杆会被拒绝并指向 `Hear`——否则写入电平会顺带把这一路声音放到输出上。改动之后场景持有这个数值、条目也持有它，而滑杆与标签都读场景，因此不会出现「界面仍是 100%、输出已是 25%」。改变电平同样不碰场景的静音。

窗口场景 `mixer` 使用本构建真实的形态：一次只路由一路声音，未对齐前被保护性静音，另一路不在场景里。它最后对未路由源做一次被拒绝的电平改动，并把 25% 一路带到滑杆与状态行。它先对未路由源 Solo 看拒绝，再对已路由源 Solo，然后主静音再解除。可听性在真正重要的地方测量：独立进程采样默认渲染端点的峰值，场景的每个相位都带时间戳，因此读数可以逐窗口对比（`mutehold` 只做「听到 → 静音 → 听到」，专门用于这项对比）。窗口的 `Hear` 是排他的，所以「Solo 从一路切到另一路」另用场景同时持有两路来验证：第二路必须先被显式允许，未对齐保护优先于路由，Solo 不是绕开它的办法；切换期间另一路的播放器被静音，退出后两路各自回到场景持有的 0.80 与 0.60。Solo 也不会替目标解除它自己的静音：被静音的目标 Solo 后仍不可听，行里同时列出「被 Solo」与「自己静音」两个理由，取消静音后才恢复。
### 监听覆盖层（P17.4a）

静音、主静音与独奏是一个**监听覆盖层**，不是混音总线。Scene 继续说明谁被路由、各自电平多少；覆盖层只决定此刻实际听到什么：

- **单源静音**只让那一路安静，不改变它存储的电平，也不改变它在路由中的位置。
- **主静音**在开启期间让所有源安静，关闭后回到各源自己的说法。
- **独奏**只保留一个源可听、其余安静；再点同一源退出，点另一个源则切换。其他源的音量、静音与路由不变，因此退出独奏后混音回到「各源现在的说法」，包括独奏期间做过的改动。

未对齐保护优先：对一个 Shift 未知的源独奏，不会悄悄解除保护，命令会直接说明。目标不在 Scene 路由里时独奏被拒绝（否则只会白白静音其他源）；目标离开会话时独奏被清除并写日志。

`apply()` 把有效静音合成为「Scene 电平自身的静音 ∨ 源自己的静音 ∨ 主静音 ∨ 独奏排除 ∨ 未对齐保护」，然后才告诉播放器。改变音量会保留 Scene 上已有的静音，因此拖动滑杆不会把静音轨重新打开。

本版本没有共享 PCM 总线：没有 ducking、平移、EQ 或输出设备切换，界面不得提供这些。详见 `testplace/evidence/P17/mixer-inventory.md`。
### 比较给出了什么，以及它是否仍然成立（P17.2）

一次探测比较两段音频并给出一个偏移。inspector 把它当作一份账户展示，而不是一个数字：

- **比了什么**：两个源、各自被解码的 Track、两个窗口，以及在建议偏移处真正重叠了多少。四秒重叠得出的建议与三十秒重叠得出的建议是两种不同强度的证据。比较解码的是 `0:a:0`，所以窗口写的是它读过的音频轨；没有音频轨的源会被拒绝，而不会被描述成画面。
- **有多强**：峰值、次候选及它出现的位置、以及由两者差距算出的 confidence。峰值 `1.000` 对次候选 `0.105` 是匹配；两个峰值只差一丝就不是，这些数字在任何人应用它之前就说明了这一点。
- **会改变什么**：建议偏移、时间轴当前持有的偏移、以及两者之差。
- **是否仍然成立**：探测会记录开始时的状态，因此探测期间或之后发生的一次 Nudge 会把这份账户变成 `expired: …` 并给出原因。状态条也用同一份报告渲染摘要，所以它不会对已经移动过的会话继续说 `now +0.000s`。

最近一次比较根本没跑完时，失败是第一行，任何更早的建议都被标为「更早的一次比较」——测量失败的会话不能看起来像刚测出了什么。失败行只描述它自己比较的那一对源与轨道；更早的建议保留在下面，但它属于更早的一次，不会被当成这次失败的目标。探测的完成以发起时记下的序号为准：只有当前这次的结果会更新账户，被后来者取代的那次即使后完成也只进日志。

这份账户是只读的：它由一次已完成的建议加上当前会话推导而来，绘制它不写入任何 Shift，因此重绘窗口不会对齐任何东西。区块的颜色跟随最近一次比较：最近一次失败即用告警色，即使更早的建议仍然有效；失败清除后，颜色才回到那份建议自身的状态。被拒绝的比较保留它的测量值——窗口与峰值照常显示，因为这才是让拒绝可核查的依据——但它从不显示建议。
### 只读地读时间轴（P17.1）

dock 是会话「真正知道什么」的只读视图，每个源一行：Track 以及它是不是同步组的参考、offset 的来源、offset 本身、时间轴把共同事件时间映射出的媒体时间，以及播放器自己报告的那个时钟。

三件事分开放，因为它们回答的是不同问题：

- **共同事件时间**是播放头持有的共享时间。
- **映射媒体时间**是 `core.Timeline.MediaTime` 对该事件给出的结果。它是请求，不是测量；没有 Shift 的 Track 上是 unknown。
- **播放器位置**是播放器自己报告的。正在显示录像的播放器报的是该文件内的位置，所以行里写 `file`，其余写 `stream`；文件位置不是缓冲的内容时间（见 P16 的时钟契约）。

没有 Shift 的 Track 读作 `not aligned`，不读作 `+0.0s`：未知与「恰好校准到零」是两件不同的事实，而 dock 以前对两者打印同一个数字。参考来自真实存在的同步组，而不是窗口里的第一个源；当参考轨道属于某个源时，那一行描述的就是参考轨道本身——Core 允许音频轨作参考，永远优先画视频会藏起同步组真正对齐的那条轨。

画出这个视图是纯读：不设置 Shift、不移动播放头、不触碰播放器，因此重绘 dock 的那一帧不会改变谁对齐了什么。
### 一次回看能对外说什么（P16.4c）

`desktop/replay_report.go` 为每笔事务保留一份账户，并把两件容易混淆的事分开：

- **阶段**描述事务本身：`preparing`、`committed`、`refused`、`rolled back`。只有 `committed` 能作为「已切换」发布；被回滚的事务保留它测到的位置，但永远不作为成功展示；被拒绝的请求带着拒绝理由。
- **证据**描述每一路：请求的位置、播放器报告的位置、以及两者之间的残差。落位只报成落位，`FrameConfirmed` 恒为 false——引擎报告的是位置，这个版本里没有任何东西能确认该位置的画面就在屏幕上。

账户是会话里的不可变值：`lastReport` 返回副本，调用方既不能靠等待把回滚变成成功，也不能改动自己手上的那份；它也不直接读事务的实时簿记。工作台把这个账户只读地画在 inspector 里：按阶段着色（`committed` 才是成功色，拒绝与回滚各自如实显示），且只经 `lastReport()` 读取，因此仍在准备中的事务不会显示成一次已经发生的回看。
由此还有两个细节。某一路「是否取得位置」由事务的 measured 标志决定，而不是看数值：目标 10ms、播放器确实报告 `0s` 也算测到了，报告里保留 `requested 10ms, reported 0s, residual -10ms`（按 `time.Duration` 原样写毫秒，不四舍五入成 0s）。账户也不会倒退：先结束、后发布的事务仍进日志，但不能覆盖比它更新的请求的账户，界面因此不会用旧的成功盖住新的拒绝。
## Web 客户端

`web/` 是一个 Go 包（`package main`）加三份静态文件。同一个进程做三件事：把页面嵌入二进制并对外提供，把一次 Core 会话以 JSON 暴露给页面，以及在 `/media/` 下提供测试媒体。它只绑定回环地址（`-addr` 不是回环地址时直接退出），启动时打印带令牌的地址；令牌只在引导地址里出现一次，随后由 HttpOnly、`SameSite=Strict` 的 cookie 承担，页面立即把它从地址栏移除，本机 Host 用 `X-MuxShift-Token` 头，`/api/` 与 `/media/` 都要求令牌。改状态的请求还要通过两道检查：请求体必须是 JSON（纯 HTML 表单发不出来），`Origin` 必须与请求主机一致；每个请求的 `Host` 也必须是回环主机，这样即使某个域名解析到本机也进不来。响应不带 CORS 头。媒体用 `os.OpenRoot` 打开，`..`、符号链接与目录联接都无法逃出 `-media-root`；一次场景改动要么整体生效要么整体回滚，非法音量不会留下半改的状态。

页面用 hls.js（`web/vendor/` 里的 1.7.4 light 构建，Apache-2.0）叠加 Media Source Extensions 播放 HLS，MP4 直接交给媒体元素。`GET /api/session` 给出源、轨与当前场景，`POST /api/scene` 用 `SetSceneVideo` 与 `SetSceneAudio` 改场景，和桌面端共享同一套 Core 语义：画面来自一路、声音可以来自另一路、音量与静音各自独立，未选中的音轨被移除并静音。

浏览器与桌面端的能力差异是明确的，不做等价假设：Web 端不参与跨源对轴，不保留历史窗口，Seek 只能落在已缓冲范围内，直播播放列表从直播边缘开始；浏览器要求用户交互后才允许出声，因此所有源一开始静音，第一次点击后才放开场景里被听见的那一路。播放失败以 hls.js 的错误类型或媒体元素错误码显示，不隐藏也不假装播放成功。

## 浏览器扩展与本机 Host

`extension/` 是一个 Manifest V3 扩展，权限只有 `activeTab`、`scripting` 与 `nativeMessaging`，没有主机权限，因此用户不点击就读不到任何页面。用户点击后，后台脚本在被激活的标签页里执行一次只读扫描：收集 `video`、`audio`、`source` 的 `src` 与 `currentSrc`，以及看起来像媒体的资源条目；`blob:` 与 `mediasource:` 地址属于页面自身，会被拒绝并说明「页面自己持有分片、没有可导入地址」，带凭据的地址直接拒绝。

用户确认其中一个地址后，扩展用 `chrome.runtime.sendNativeMessage` 调用本机 Host `com.muxshift.bridge`；Native Messaging 只传这条控制消息，不传媒体。Host 是 `extension/host/` 里的 Go 程序，它首先核对第一个参数里的调用方 origin 必须等于 `manifest.json` 中固定 `key` 推出的扩展 ID（`chrome-extension://agacmebmmcbkblmekgdkfcehehccl/`），然后读取会话写下的 `%LOCALAPPDATA%\MuxShift\bridge.json`（地址与桥接令牌，权限 0600），用该令牌以 `X-MuxShift-Bridge` 头调用 `POST /api/import`。桥接令牌与页面令牌是两个不同的值：前者只存在于本机文件与 Host 之间，后者只到页面，因此页面即使带着自己的 cookie 也导入不了任何东西；日志只记录导入地址的 scheme、host 与路径，带签名参数的地址不会把凭据写进日志。需要说明的是，`allowed_origins` 与第一个参数里的 origin 是浏览器在扩展与 Host 之间执行的约束，不是对本机其他进程的强身份认证——那类进程可以自己启动 Host，真正拦住它的是它拿不到的桥接令牌。

会话对导入地址做同样严格的检查：只接受 `http(s)`、必须有主机、拒绝带凭据的 URL、拒绝重复登记；然后走与其它源相同的 `AddSource` 与 `AddTrack`，所以扩展无法直接改时间轴或碰桌面端私有实现。页面每两秒读一次会话，导入的源无需刷新就出现；跨源地址按目标站点的 CORS 规则播放，本地服务不做代理，受保护媒体一律不碰。扩展不提供标签页采集：采集得到的是只有浏览器能解码的实时流，而本地会话接收的是可播放地址或文件，因此在弹窗里直接说明这一点而不是假装能捕获。

## 人声分离实验

`tools/separate/` 把一段录音分成「人声」与「非人声」两份 WAV，用 UVR MDX-Net 导出的 ONNX 模型做分块推理。它不是播放路径的一部分：桌面端与 Web 端都还没有调用它，也没有把它做成用户可见的开关。实现按参考工程 `ultimatevocalremovergui` 的 `STFT` 与 `demix` 对齐——44.1 kHz 立体声、6144 点 Hann 窗、hop 1024、保留 3072 个频点，每块 `hop * (dim_t - 1)` 样本并做 Hann 重叠相加，非人声轨取「混合 − 人声」。模型输入输出都是 `[1, 4, 3072, 256]`。

在这台 RTX 4060 Laptop（8 GiB）上实测：DirectML 每 5.92 秒的块约 0.26 秒（约 7.8 倍实时，显存约 6.2 GiB），纯 CPU 每块约 5.75 秒（慢于实时）。5.92 秒是**一次模型输入块的长度**，不是实测的端到端延迟：分块重叠、调度、编码、缓冲与播放器启动都会叠加到听众实际等待的时间里，这些都没有测量，因此也不能把 5.92 秒直接写成两个 Source 之间的固定偏移。合成样例（TTS 解说 + 合成环境声）上人声轨与解说源相关 0.99、非人声轨与环境声源相关 0.83，重建误差 3e-5；换成真实录音（LibriVox 公版朗读 + Wikimedia 公版掌声，20 秒、掌声 0.8 倍）后，人声轨与朗读源相关 0.93、非人声轨与掌声源相关 0.94，重建误差 2e-5。真实球场转播里的解说仍未验证。两份 WAV 是同一段录音的派生音轨，不是两路独立直播源：真正接入时要把来源、采样率、原始时间轴与处理延迟一起保留，跨源偏移只能来自内容时间戳。

权重许可未确认：代码仓库声明 MIT，权重发布仓库没有 LICENSE，相关 issue 未得到答复。因此模型只放在被忽略的 `testplace/models/`，脚本要求显式传入 `--model`，仓库与发布包都不打包权重。

## 自动对轴探测实验

`tools/align/` 只用内容本身回答「两段记录相差多少」：`match.py` 把 WAV 降成 16 kHz、10 ms 一跳的对数能量包络，用 FFT 互相关找出最佳 lag；`frame_hash.py` 用 ffmpeg 按固定帧率抽帧、缩成 16x16 灰度缩略图，再按 lag 求平均相关系数。两者都输出最佳候选、次佳候选与最佳相对全部候选的中位水平之差，达不到阈值就拒绝并说明原因，而不是挑一个最高峰宣布对齐。

第二个阶段的只读建议落在 `core/align` 与 `desktop/align.go`：`Compare` 在 Go 侧对两段 16 kHz、10 ms hop 的 RMS 包络做逐 lag 的归一化相关，峰值 ±500 ms 内的 lag 视为同一个峰，次佳峰与主峰的差距给出 confidence；参与比较的重叠长度按两段窗口较短的那一段与实际 lag 计算，少于 `MinOverlap`（默认 10 秒）或最短窗口的四分之一都直接拒绝，避免用几帧的偶然相关当候选。桌面端的「试着对齐」按钮读两路授权音频（桌面端拿不到解码后的 PCM，所以用 ffmpeg 解同一个地址），按 `CoreOffset = (MediaStart_B − MediaStart_A) + LocalMatchOffset` 换算成 Core 偏移，显示建议值、与当前偏移的差值、`matched X of Y` 或拒绝原因。解码在 UI 线程之外进行，窗口照常重绘；探测开始时先记下两段窗口、播放器代次、目标偏移与同步组，结果返回时与这份快照比较，任一变化只把结果标为过期而不是并入建议。它**不接入播放**，也**不写时间轴**：桌面端仍只有 P7 的手动 ±0.1 秒会改变播放位置，`Timeline` 的写入方只有桌面端的同步代码。原因是要避免「自动结果覆盖用户已调好的偏移」，以及在没有共同内容时给出自信的错误答案。这次比较的上下文属于会话（P18.3）：关闭窗口会取消 ffmpeg 子进程，而不是让它再解三分钟；被取消的那次比较的编号已经前移，迟到的结果只会被当作过期丢弃，不会变成会话的账目；关闭本身不等绘制线程，而「试着对齐」在比较进行中仍然拒绝第二次比较。

实测（180 秒朗读录音、`--max-lag 60`）：预制 2、15、45 秒偏移全部估对（分辨率即 10 ms 包络 hop），插入 3 秒静音的一对估出 +3 秒，加混音的一对估出 0 秒；不同录音、拼接重播与 1.05 倍变速三对全部被拒绝。音频对一次约 0.1 秒。视频侧在合成画面上能找到正确 lag，但这类画面在所有 lag 上都相似，置信度规则按规定拒绝；公版真实比赛录像的下载被 HTTP 429 挡住，因此视频路径只算实现、未验证。细节与数字在 `tools/align/README.md`。

## 边界原则

- 支持独立媒体源和多个同步组；不把「双路」作为 Core 的固定数量限制。
- 媒体源、音轨、同步关系、输出布局是不同概念。`core` 已固定它们的形状、事件时间轴、HLS 元信息读取与有界回看缓冲；桌面端已能在会话里登记多个媒体源、按场景选择画面与声音、各自调整音量，手动把一路对到另一路上，为直播源保留有限历史窗口并把其中一段切成录像、在会话里播放与跳转；Web 端能在浏览器里真实播放多路源并切换画面与声音，浏览器扩展能把用户选中的页面地址交进同一个会话；人声分离只有未接入播放的实验脚本，自动对轴只有一个只读的探测脚本；采集、混音、自动跨源同步、把回看窗口当作可 Seek 的授权区间，以及分离结果的实时接入尚未实现。
- 浏览器会话访问和跨端媒体能力存在差异；不能默认 Web 可以读取 Edge Cookie 或任意第三方媒体流。
- Go Core 与 MyGo 的 UI 生命周期分离。桌面端当前用 MyGo 的原生播放，其它媒体引擎、音频推理与传输协议尚未确定，不把候选技术写成已集成依赖。
- `testplace/` 不进入版本控制；正式文档仅维护稳定且可验证的仓库事实。

可执行的验证入口、每项检查覆盖什么、哪些只能在真窗口里跑，见[验证索引](VERIFICATION.md)。要点：仓库根目录与 `desktop/` 是两个 Go module，各自跑 `go test ./...`；桌面端的播放、切换、回看与布局结果不进入单元测试，由 `desktop` 的场景脚本在 Windows 的真实窗口里测量；Web 客户端的真实播放要在浏览器里核对（Chromium 与 Edge 实测通过，未安装的浏览器记为 not_run）；本机 Host 与扩展的桥接在 Edge 里以未打包方式手工验证；人声分离与自动对轴脚本不属于 Go 模块，各自的数字见 `tools/separate/README.md` 与 `tools/align/README.md`。
