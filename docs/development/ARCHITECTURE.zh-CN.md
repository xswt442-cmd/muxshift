# 工程架构

[English](ARCHITECTURE.en.md)

当前仓库是工程骨架，已实现的部分是 Go Core 的会话配置模型、事件时间轴、从 HLS 播放列表读取轨道与时间信息、有界的直播回看缓冲，以及两个客户端：一个用 MyGo 原生播放的桌面实验应用，一个用 hls.js 在浏览器里播放的 Web 客户端。两者都在同一个会话里登记多个媒体源，由场景决定显示哪路画面、听见哪路声音。尚未实现跨源同步、混音与多路受控播放；回看缓冲与把它拼成的录制文件成立，但在运行中的会话窗口里显示回看画面没有成立。

## 模块及边界

| 目录 | 当前状态 | 职责边界 |
| --- | --- | --- |
| `core/` | 会话配置模型 | 共享的媒体会话配置与控制契约所在位置 |
| `core/hls/` | HLS 元信息读取 | 读播放列表、轨道与首个样本时间，不转码、不对外供流 |
| `desktop/` | MyGo 桌面实验应用 | 把多个媒体源登记进一个 Core 会话，按场景显示画面与听见声音，并管理播放器生命周期；不承载共享业务逻辑 |
| `web/` | Web 客户端（hls.js 与 MSE） | 只监听本机的会话服务与静态页面；播放能力受浏览器限制，不假装等同桌面 |
| `extension/` | 浏览器扩展与本机 Host | 把用户点击后选中的那一个页面地址交给正在运行的会话；不复制 Cookie、请求头或密钥 |
| `testplace/` | 本地忽略目录 | 实验、临时记录、Agent 工作文件 |

客户端与 Core 的预期依赖方向为 `desktop → core ← web`；浏览器扩展通过显式协议衔接，不直接耦合桌面 UI。这里描述的是模块所有权约束，不代表这些调用已经实现。

## Core 会话模型

`core.Session` 只保存配置，不保存播放状态。一个会话持有它读取的媒体源、源中发现的音视频与字幕轨、把多条轨绑到同一参考轨的同步组、决定显示什么与听见什么的场景，以及把场景交给某个能力的输出。每条轨最多属于一个同步组。每次操作要么完整生效，要么不改动会话；被拒绝的操作不记录事件；删除媒体源会同时删除它的轨以及对这些轨的全部引用。

## Core 事件时间轴

`core.Timeline` 用 `targetMediaTime = sharedEventTime + mappedOffset` 把同一个共同事件时间映射到各条轨的媒体时间。偏移为正表示该轨的媒体时钟走在前，按直播跟随需要把它延后同样的时长；偏移为负表示该轨还没到达当前事件的内容。设置偏移是替换而不是叠加，因此同一校准结果应用两次不会累积。没有偏移的轨按 `not_aligned` 报告，不会被放到猜测的时间上。

`core.Playhead` 是共同事件时钟：从零开始且处于暂停，只有播放时才前进；跳转保留当前暂停或播放状态。暂停、恢复与跳转一起移动这个时钟和每一条轨的目标时间，从不改动已存的偏移。`Timeline.AdjustShift` 在已存偏移上加减一个步长并返回新偏移，用「从当前偏移出发」的方式保证连续按十次 0.1 秒就是 1 秒；溢出时返回 `core.ErrTimeRange` 并保留原偏移。这两个类型都不解码媒体、不操作播放器、不访问网络。

## HLS 元信息读取

`core/hls` 只做两件事：读一个 HLS 播放列表的描述，以及读出它包含的音视频轨与每条轨的首个样本时间。它用 `gohlslib` 解析播放列表与分片，不手写 parser，也不下载多余分片。`Read` 只接受媒体播放列表，主播放列表由调用方选择变体；`Probe` 接受主播放列表，由库选择默认变体。

轨道的 PTS 只在同一条流内有意义：库会把时间戳归一化到该流的首个样本。`EXT-X-PROGRAM-DATE-TIME` 声明的墙钟时间能建立候选的跨流时间参考，但两个不同直播源里相同的墙钟时间不保证对应同一个比赛事件：导播、转码与缓冲都会改变内容与时间的关系。因此 `Align` 给出的是候选偏移，不宣称完成内容级对齐。缺少该声明时返回 `core.ErrNotAligned`，不猜一个精确匹配。`Attach` 把流建成 Core 的媒体源与轨，失败时回滚到调用前的状态；`Apply` 校验后再把偏移写入 `core.Timeline`。

地址只接受 http 与 https，拒绝带凭据的 URL；从公网地址发起的重定向不允许落到本机或内网地址。超时、取消与非 200 响应都以可判别的错误返回，不会把明文凭据写入日志。

## 桌面适配（MyGo）

`desktop/` 是一个 MyGo 实验应用，它把命令行给出的每个本地文件或 http(s) 地址登记成一个 Core 媒体源：网络来源先用 `core/hls` 读出真实轨道再登记，本地文件登记成一条视频轨与一条音频轨（MyGo 不枚举本地文件的轨道）。会话里有一个场景和一个桌面窗口输出，场景决定显示哪条视频轨、听见哪条音频轨以及各自的音量与静音；界面上的按钮只改场景，`apply()` 再按场景设置每个播放器的显示、静音与音量。

一个媒体源对应一个播放器实例，这是桌面适配当前的实现策略，不是 Core 的约束：Core 只描述媒体源、轨与场景。未被场景选中的视频不是从视图里删除，而是保持播放器存活并隐藏。

播放器的创建、显示、停止显示与关闭由同一个组件按顺序处理：关闭时在同一主线程回调里把来源标记为不显示并让指针失效，等窗口真的建出三帧，再在主线程调用 `Close()`；唤醒首帧的异步任务带实例代次，代次不符立即退出。重新打开同一来源采用交接式顺序：先打开新播放器，旧的继续绘制，等新的就绪后再关闭旧的，因为此构建在两个视频元素之间出现空档时新播放器不会拿到首帧。

交接有明确失败边界：新播放器在超时内没有画面时，旧播放器继续绘制并继续播放，被关掉的是没起来的新播放器，来源行报告原因；一旦新播放器有画面，旧的才释放。每次交接都绑定实例代次，连续快速点重新加载时只有最后一轮拥有该来源，交接对象随代次转移，所以同一播放器不会被关两次，旧回调也不会错误关掉新播放器。

此构建的 `ui/video` 有几处缺口，应用层做了补偿并如实记录：网络来源自己不交付首帧，需要一次向前的跳转（只在打开阶段补偿一次，跳转后的位置从播放器重新读取，不用假设值；补偿失败就保持未就绪状态并把实际错误显示出来，后台不会反复改动播放位置）；同一窗口里有两个视频或视频还没交付帧时 `CapturePage` 会读到空缓冲区并 panic，截图因此包了 `recover`；从未显示过的播放器位置不推进，所以「A 画面 + B 声音」要等 B 至少显示过一次；把界面上正在显示的视频元素换掉会让窗口停止重绘，因此所有播放器的视频元素始终在树上，只切换显示状态。

声音不靠听感判断：`IAudioMeterInformation` 只读采样默认输出设备的峰值，播放时有电平、静音后为 0、两路同时出声时电平更高。它不能区分是哪个进程在发声，因此每个采样窗口只运行被观测的应用并对齐时间。

手动对轴在 `desktop/sync.go`：`Timeline` 保存每条轨的偏移，`Playhead` 保存共同事件时间。暂停与恢复按会话里**一个显式的 Core 同步组**下发：第一次同步命令（暂停、恢复、锚定或微调）时，用当时场景选中的源建出这个组并固定成员，之后改变场景不会改变成员；组外的源继续播放，失败成员按源名上报。这样安排是因为一个场景以后可能同时显示两场互不相关的比赛、各自有同步组，按场景判断会把两场一起暂停。对某一源按 ±0.1 秒时，先把该源的偏移加减一步，再按 `事件时间 + 偏移` 定位播放器；目标早于流起点时拒绝并说明原因，不改另一路的速度。锚定把参考播放器的当前位置作为事件时间，因此重复锚定不会让目标漂移。未在时间轴上定位过的源默认静音，界面上的例外按钮可以放开或撤回——这是防剧透的可见、可恢复路径。

播放器报告的 `Position()` 是各条流自己的时间，不是内容时间：两条流的起点不同，同一位置上的内容也不同。跨源比较必须用内容标记（例如画面内嵌时码），实测剩余误差约 0.1 秒，来自 seek 落点与位置回报。

回看窗口在 `core/dvr` 与 `desktop/dvr.go`。`core/dvr` 把一个源的分片按序号存成文件：不是传输流的分片被拒绝，序列号跳号或下载失败时留下一条缺口而不是抹掉，两端都有节目时间时用它们量出缺口长度，并对外报告真实连续的可用区间。`Retention` 与 `MaxBytes` 限制目录大小，`Evict` 只删除未被保护的最旧分片，`Close` 删除文件与它自己创建的目录。`Join(from)` 把 `from` 所在的那段连续区间按顺序拼成缓存目录里的一个传输流文件，落在分片中间的开始时间从该分片首帧起，跨缺口就拒绝，所以得到的文件本身可以播放；录制文件归缓冲区所有，下一次 `Join` 替换上一份，`Close` 把它和分片一起删除，因此目录不会被一份打开的录制撑大。

录制文件的时间轴与共同事件时间不是一回事：文件从它拼接的第一段的首帧开始，位置 `p` 对应内容时间「首段起点 + p」，而首段起点是包含 `from` 的那一段的开头，通常比 `from` 早不到一个分片。要把回看位置放回共同事件时间，必须和缓冲一样加上该源的 `mappedOffset`，并额外记住这次 `from` 与该段首帧之间的差；只按 `from` 推算会把误差算到对齐结果里。

桌面端每秒读一次直播源的播放列表写进这样的缓冲区，读取与画面无关：暂停输出不会暂停输入，这一点由 P8 实测记录。两路缓冲按与时间轴相同的偏移规则把各自的 `Available()` 换算到共同事件时间再求交集；没有已知偏移时返回错误而不是猜测，区间不重叠时如实报告而不是悄悄丢掉一路。

把录制放进正在运行的窗口还没有实现：`Join` 产出的文件作为唯一源、在单独启动的进程里打开时会真实播放并前进（位置从 1.26 秒走到 2.26 秒，画面内嵌时码与之相符），`desktop` 的 `-replay` 模式就是这种用法；但把它放进一个已有其它源的窗口、或为它新开一个窗口时，播放器回报 `ready=false`、位置停在 0，跳转只改变报告的位置而不出画面。因此「会话内回放」明确记为未实现，先前试过的本机 HTTP 出口因为没有任何改善已经删除。

缓存里的分片只做了结构检查：长度是 188 字节的整数倍、每个包的首字节是同步字节，并且拒绝无法读取或不是传输流的内容；这不能保证每一帧都能解码。因此现在的准确说法是「有限 HLS 分片缓存、基于已缓存分片的连续区间查询与录制拼接」，录制文件的播放只在 Windows 上以 MyGo 单源方式验证过。

## Web 客户端

`web/` 是一个 Go 包（`package main`）加三份静态文件。同一个进程做三件事：把页面嵌入二进制并对外提供，把一次 Core 会话以 JSON 暴露给页面，以及在 `/media/` 下提供测试媒体。它只绑定回环地址（`-addr` 不是回环地址时直接退出），启动时打印带令牌的地址；令牌只在引导地址里出现一次，随后由 HttpOnly、`SameSite=Strict` 的 cookie 承担，页面立即把它从地址栏移除，本机 Host 用 `X-MuxShift-Token` 头，`/api/` 与 `/media/` 都要求令牌。改状态的请求还要通过两道检查：请求体必须是 JSON（纯 HTML 表单发不出来），`Origin` 必须与请求主机一致；每个请求的 `Host` 也必须是回环主机，这样即使某个域名解析到本机也进不来。响应不带 CORS 头。媒体用 `os.OpenRoot` 打开，`..`、符号链接与目录联接都无法逃出 `-media-root`；一次场景改动要么整体生效要么整体回滚，非法音量不会留下半改的状态。

页面用 hls.js（`web/vendor/` 里的 1.7.4 light 构建，Apache-2.0）叠加 Media Source Extensions 播放 HLS，MP4 直接交给媒体元素。`GET /api/session` 给出源、轨与当前场景，`POST /api/scene` 用 `SetSceneVideo` 与 `SetSceneAudio` 改场景，和桌面端共享同一套 Core 语义：画面来自一路、声音可以来自另一路、音量与静音各自独立，未选中的音轨被移除并静音。

浏览器与桌面端的能力差异是明确的，不做等价假设：Web 端不参与跨源对轴，不保留历史窗口，Seek 只能落在已缓冲范围内，直播播放列表从直播边缘开始；浏览器要求用户交互后才允许出声，因此所有源一开始静音，第一次点击后才放开场景里被听见的那一路。播放失败以 hls.js 的错误类型或媒体元素错误码显示，不隐藏也不假装播放成功。

## 浏览器扩展与本机 Host

`extension/` 是一个 Manifest V3 扩展，权限只有 `activeTab`、`scripting` 与 `nativeMessaging`，没有主机权限，因此用户不点击就读不到任何页面。用户点击后，后台脚本在被激活的标签页里执行一次只读扫描：收集 `video`、`audio`、`source` 的 `src` 与 `currentSrc`，以及看起来像媒体的资源条目；`blob:` 与 `mediasource:` 地址属于页面自身，会被拒绝并说明「页面自己持有分片、没有可导入地址」，带凭据的地址直接拒绝。

用户确认其中一个地址后，扩展用 `chrome.runtime.sendNativeMessage` 调用本机 Host `com.muxshift.bridge`；Native Messaging 只传这条控制消息，不传媒体。Host 是 `extension/host/` 里的 Go 程序，它首先核对第一个参数里的调用方 origin 必须等于 `manifest.json` 中固定 `key` 推出的扩展 ID（`chrome-extension://agacmebmmcbkblmekgdkfcehehccl/`），然后读取会话写下的 `%LOCALAPPDATA%\MuxShift\bridge.json`（地址与令牌，权限 0600），用该令牌调用 `POST /api/import`。令牌始终留在本机文件与 Host 之间，扩展拿不到，页面也读不到。

会话对导入地址做同样严格的检查：只接受 `http(s)`、必须有主机、拒绝带凭据的 URL、拒绝重复登记；然后走与其它源相同的 `AddSource` 与 `AddTrack`，所以扩展无法直接改时间轴或碰桌面端私有实现。页面每两秒读一次会话，导入的源无需刷新就出现；跨源地址按目标站点的 CORS 规则播放，本地服务不做代理，受保护媒体一律不碰。扩展不提供标签页采集：采集得到的是只有浏览器能解码的实时流，而本地会话接收的是可播放地址或文件，因此在弹窗里直接说明这一点而不是假装能捕获。

## 边界原则

- 支持独立媒体源和多个同步组；不把「双路」作为 Core 的固定数量限制。
- 媒体源、音轨、同步关系、输出布局是不同概念。`core` 已固定它们的形状、事件时间轴、HLS 元信息读取与有界回看缓冲；桌面端已能在会话里登记多个媒体源、按场景选择画面与声音、各自调整音量，还可以手动把一路对到另一路上，并能为直播源保留有限历史窗口；Web 端能在浏览器里真实播放多路源并切换画面与声音，浏览器扩展能把用户选中的页面地址交进同一个会话；自动跨源同步、混音与回看播放本身尚未实现。
- 浏览器会话访问和跨端媒体能力存在差异；不能默认 Web 可以读取 Edge Cookie 或任意第三方媒体流。
- Go Core 与 MyGo 的 UI 生命周期分离。桌面端当前用 MyGo 的原生播放，其它媒体引擎、音频推理与传输协议尚未确定，不把候选技术写成已集成依赖。
- `testplace/` 不进入版本控制；正式文档仅维护稳定且可验证的仓库事实。

目前可执行的基础验证是仓库根目录的 `go test ./...`，它运行 `core` 的会话与时间轴测试、`core/hls` 对录制样例的读取测试，以及 `core/dvr` 的缓冲测试。桌面应用的构建与真实播放需要在 Windows 上单独验证：`cd desktop && go build .`，播放、多源、声音、手动对轴与回看结果不进入单元测试，只在 Windows 上手工验证。Web 客户端用 `go build ./web` 验证构建，真实播放要在浏览器里核对（Chromium 与 Edge 实测通过，未安装的浏览器记为 not_run）。本机 Host 用 `go build ./extension/host` 验证构建，扩展与 Host 的桥接在 Edge 里以未打包方式手工验证。
