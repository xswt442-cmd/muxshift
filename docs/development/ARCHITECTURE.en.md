# Architecture

[简体中文](ARCHITECTURE.zh-CN.md)

This repository is a working early prototype, not a finished application. Implemented: a Go Core session configuration model and its event timeline, HLS playlist metadata reading, a bounded replay buffer for live segments with recording cuts, and three clients — a desktop app that registers several sources into one Core session, lets a scene decide which picture is shown and which sound is heard through MyGo's native video path, a web client that plays HLS in the browser through hls.js, and a browser extension that hands the address a user picked to the local session. The desktop app also aligns sources by hand, imports a source while it runs (the imported card does come up with a picture), cuts a recording out of the buffer and plays and seeks it in the session window, and persists settings and folds its layout between 100% and 200% scaling. Not implemented: media capture, mixing, automatic cross-source synchronization, controlled multi-source playback, and treating a replay window as an authorized seek range (P16.4 is blocked); the extension's real toolbar click is still unverified.

## Modules and ownership

| Directory | Current state | Responsibility boundary |
| --- | --- | --- |
| `core/` | Session configuration model | Shared media-session configuration and control contracts |
| `core/hls/` | HLS metadata reading | Reads playlists, tracks, and first sample times; no transcoding and no serving |
| `desktop/` | MyGo desktop experiment | Registers several sources into one Core session, shows and hears what its scene selects, and owns the player lifecycle; no shared business logic |
| `web/` | Web client (hls.js and MSE) | Loopback-only session service and static page; browser limits stay visible instead of being assumed equal to the desktop |
| `extension/` | Browser extension and native host | Hands the one page address the user picked to the running session; copies no cookies, headers, or keys |
| `tools/separate/` | Experimental script | Splits one recording into vocal and non-vocal WAV files with a model you supply; not on the playback path and the weights are not published with the repository |
| `design/`, `tools/designtokens/` | Design tokens and generator | Colours, radii, spacing and type sizes live only in `design/tokens.json`; it generates `web/tokens.css` and `desktop/tokens.go`, and both clients consume the generated files |
| `testplace/` | Ignored local directory | Experiments, temporary notes, and agent working material |

The intended client-to-core dependency direction is `desktop → core ← web`; the browser extension integrates through an explicit protocol instead of depending on the desktop UI. These are ownership constraints, not existing runtime calls.

## Core session model

`core.Session` holds configuration only, never playback state. A session owns the sources it reads, the tracks found in them, sync groups that bind tracks to one reference track, scenes that decide what is shown and heard, and outputs that hand a scene to a capability. Each track belongs to at most one sync group. Every operation either applies completely or leaves the session unchanged, a refused operation records no event, and removing a source removes its tracks and every reference to them.

## Core event timeline

`core.Timeline` maps one shared event time to each track's media time with `targetMediaTime = sharedEventTime + mappedOffset`. A positive offset marks a track whose media clock runs ahead, so following it live means holding it back by that offset; a negative offset marks a track that has not reached the current event yet. Setting an offset replaces the previous one, so applying the same calibration twice does not accumulate. A track without an offset is reported as `not_aligned` instead of being placed at a guessed time.

`core.Playhead` is the shared event clock: it starts paused at zero, advances only while playing, and seeking keeps the paused or playing state. Pause, resume, and seek move this clock and every track's target together; they never change a stored offset. Neither type decodes media, seeks a player, or talks to a network.

## HLS metadata reading

`core/hls` does exactly two things: read the description of one HLS playlist, and read the audio and video tracks it carries with each track's first sample time. It uses `gohlslib` to parse the playlist and the segments, does not hand-write a parser, and does not download segments it does not need. `Read` accepts a media playlist only, leaving variant choice to the caller; `Probe` accepts a multivariant playlist, where the library picks the default variant.

A track's PTS is meaningful within its own stream: the library normalizes timestamps to that stream's first sample. The wall clock an `EXT-X-PROGRAM-DATE-TIME` entry declares can give a candidate cross-stream reference, but the same wall clock in two different live sources does not guarantee the same match event: different direction, transcoding, and buffering all change how content relates to time. `Align` therefore produces candidate offsets and does not claim content-level alignment. When the declaration is missing it returns `core.ErrNotAligned` instead of guessing an exact match. `Attach` turns a probed stream into Core sources and tracks and rolls back on failure; `Apply` validates first, then stores the offsets on `core.Timeline`.

Addresses must be http or https and must not carry credentials; a redirect from a public address may not land on a local or private one. Timeouts, cancellation, and non-200 responses come back as distinguishable errors, and credentials are never written to a log.

## Desktop adapter (MyGo)

`desktop/` is a MyGo experiment. It registers every local file or http(s) address given on the command line as a Core source: a network source is probed with `core/hls` first so its real tracks are registered, while a local file is registered as one video track and one audio track because MyGo does not enumerate tracks of a local file. The session holds one scene and one desktop-window output; the scene decides which video track is shown, which audio tracks are heard, and at what volume and mute state. The buttons change the scene, and `apply()` then sets each player's visibility, mute, and volume from it.

One player per source is the desktop adapter's current strategy, not a Core rule: Core only describes sources, tracks, and scenes. A video the scene does not select keeps its player alive and is hidden rather than removed from the view.

The window shell is a workbench: a global bar on top, a rail on the left, the stage and transport in the middle, an inspector on the right, a timeline dock along the bottom, and a status bar that stays visible. The four pages — stage, sources, diagnostics, settings — live behind the rail; the inspector shows the selected source's actionable detail (show, hear, volume, ±0.1 s, try alignment, retry, remove) and the read-only session summary when nothing is selected; the dock shows the shared event time and each source's offset (read-only until P16). The rail, inspector and dock fold away with the client area (<900px folds the rail, <1160px the inspector, <660px of height the dock), and each can be switched by hand, with that choice winning over the size rule. The diagnostics page offers nothing that changes state. The settings page (P15.3) gathers the seven persisted options — start page, default volume for new sources, nudge step, whether unaligned sources start muted, master volume, the dock default, and compact spacing. Apply validates and writes the file atomically; Cancel leaves the applied values alone; Reset only rewrites the draft. The DVR and shortcuts sections are visible but disabled with their reason stated, so the interface never offers a control it cannot honour. An import reads in the background with a live seconds counter and a Cancel; a failure raises one notification (clickable through to the diagnostics page, dismissible from the status bar) and leaves no half-built source card. Ctrl+S/H/R and Ctrl+1..4 are window shortcuts, and they say so when no source is selected. Every action in the interface goes through one entry point in `desktop/controller.go`; the command carries the source identity and the player generation, its result is logged, and a snapshot is read back, so a button press, its log line, and the snapshot describe the same thing.

P13.3 also checked using a web page as the control surface inside the same window: the native video element sits on top, a MyGo web view below, and the page calls bound methods such as `Panel.Show` through `mygo.call`, which land in that same command entry point. It works, at a measured cost: the frontend and its bindings must be registered before `mygo.App.Run`, the field names the page sees depend on the lower-case JSON tags of the bound value, the page does not size itself to its element, and `CapturePage` cannot see the web view because the system view sits below the drawn content. The shell therefore adopts "native picture plus an optional web control surface", where the page may only consume commands and snapshots and the native path always remains the working fallback.


One component creates, shows, hides, and closes players. Closing marks the source as hidden and invalidates its player pointer in a single main-thread callback, waits for the window to actually draw three frames, and only then calls `Close()` on the main thread. Asynchronous first-frame work carries a generation number and stops as soon as it no longer matches. Reopening a source hands over instead of closing first: the new player opens while the old one keeps drawing, and the old one is closed once the new one is ready, because this build delivers no first frame when the window briefly has no video element at all.

The handover has an explicit failure edge. When the new player shows no picture before the timeout, the old player keeps drawing and keeps playing, the replacement that never started is the one that gets closed, and the source line reports why; a player is released only once a replacement has a picture. Every handover is bound to the instance generation, so a burst of reloads leaves the last one owning the source, the handover object moves with the generation, and no player is closed twice or closed by an older task.

This MyGo build has several gaps, which the application compensates for and records. A network source does not deliver its first picture by itself; one forward seek brings it in. That seek happens once, while the player is opening, the position after it is read back from the player instead of assumed, and if it does not work the player stays not ready and reports the real error: no background task keeps moving the playhead. It is a first-frame compensation, never a time-alignment mechanism. Two videos in the same window, or a video that has not delivered a frame yet, make `CapturePage` panic while reading an empty buffer, so captures are wrapped in `recover` and only log the failure. A player that was never drawn does not advance, so "A's picture with B's sound" only holds once B has been drawn at least once. Replacing the video element that is being drawn stops the window from repainting, so every player's video element stays in the tree and only its visibility changes.

Sound is not judged by ear: `IAudioMeterInformation` samples the default output device read-only, showing a level while playing, zero while muted, and a higher level when two sources sound at once. Those results are recorded in the P6 evidence. The meter cannot tell which process is sounding, so each sampling window runs only the observed application and aligns its log in time.


Manual alignment lives in `desktop/sync.go`: a `Timeline` holds one offset per track and a `Playhead` holds the shared event time. Pause and play are sent to the members of **one explicit Core sync group**: the first sync command — pause, play, anchor or nudge — creates that group from the sources the scene selects at that moment and fixes its membership, so a later scene change does not change who pauses; a source outside the group keeps playing, and a member that fails is reported by source name. The group is used rather than the scene because one scene may later show two unrelated matches, each with its own sync group, and a scene-based rule would pause both. A ±0.1s press moves that source's offset by a step and then seeks the player to `event time + offset`; a target before the start of the stream is refused with a reason instead of slowing the other source down. Anchoring adopts the reference player's current position as the event time, so anchoring again cannot make the target drift. A source that has never been placed on the timeline stays silent by default, and a visible button allows or withdraws that exception — the visible, reversible path against spoilers.

A player's `Position()` is that stream's own time, not content time: two streams starting at different points show different content at the same position, so a cross-source comparison has to use a content mark such as burnt-in timecode. The measured residual is about 0.1s, which comes from the seek landing point and the reported position; both are recorded in the P7 evidence.

P14 puts the engine behind one adapter: `desktop/player.go` exposes only the operations a controlled player needs — play, pause, seek, volume, mute, close — and a read-only state of ready, playing, buffering, position, duration and error, while drawing, handover and waking still use the raw player, so replacing the engine would not touch the session or the command layer. The time base is fixed in `desktop/timebase.go` as `media = event + offset`, and both conversions reject negative values and overflow. The baseline matrix — one, two and four sources plus live-and-file — is collected by `desktop/matrix_scenario.go`, which records readiness, position advance, pause freeze and picture/sound switching while CPU, working set and GPU are sampled: at four sources the peak is 9.66s of CPU per sampling window, 291 MB of working set and 25% GPU, and a position that stops advancing or a picture that does not freeze on pause counts as a failure. The lifecycle scenario covers three rapid reloads, adding and removing sources at runtime, an address that cannot open, and closing down to zero: only the last reload owns the source, window and session agree after a removal, an HLS source added at runtime can become ready, and an unreachable address fails silently (`ready=false`, `err=nil`), so the interface may only show "not ready" instead of inventing a reason. The engine decision is to keep MyGo (pinned at `5a2f9c6`, MIT): none of the gaps failed an acceptance check, and the alternatives — libmpv, a hand-written FFmpeg renderer, the WebView — all cost licence, distribution or integration work first; a timeboxed spike is allowed only when a PCM tap, multiple audio tracks per source, sub-100ms two-source control or a non-Windows client becomes a requirement, and the triggers and evidence are recorded with the P14 engine decision.

The replay window lives in `core/dvr` and `desktop/dvr.go`. `core/dvr` stores one source's segments in a directory, one file per sequence number, rejects a segment that is not a transport stream, keeps a gap instead of hiding it when a sequence number is skipped or a download fails, measures that gap from program-date times when both ends have one, and reports the contiguous ranges it really holds. `Retention` and `MaxBytes` bound the directory; `Evict` removes the oldest segments that are not protected, and `Close` removes the files and the directory it created. `Join(from)` writes the stored range that holds `from` as a new transport stream file in the buffer directory, so a start that falls inside a segment begins at that segment's first frame, a range that crosses a gap is refused, and the resulting file plays on its own. Each call publishes a new file: a published recording is never overwritten, so a player that has one open keeps reading the bytes it was given, and `Close` removes every recording the buffer published along with the segments. `Record(from)` performs the same cut and also returns a `Recording`: a unique id and file name, the requested buffer time, the buffer time of the file's real first and last frame, the sequences it holds, the ranges and gaps as they stood, the source identity, and the file's size and timestamp. The bytes go to a temporary `.<id>.part` file that is renamed only after it is complete, so a failed cut removes its own temporary file and cannot damage an earlier recording. `Recording.BufferTime(position)` is `position + StartBufferTime` on the buffer's own clock, which begins at the first segment the buffer stored, not on the source's media clock. Reaching the source clock needs a measured `Anchor{Source, BufferStart, MediaStart}`: `SourceMediaTime(position, anchor)` refuses with `ErrNoAnchor` when the anchor is missing or belongs to another source, instead of assuming the buffer started at zero. `EventTime(position, anchor, offset)` adds `StartBufferTime` to the file position and maps that buffer time through `Anchor.ContentTime` -- buffer time is the content clock the Core timeline holds -- then subtracts the confirmed track offset, because Core fixes `media = event + offset`; `SourceMediaTime` stays the explicit container-domain mapping for opening a file at a timestamp. `Valid()` reports whether the file still exists at that size. The requested time is not the file's first frame; only a request exactly on a segment boundary makes the two equal. A published recording stays while a consumer holds it: `Lease(id)` hands out a reference that the desktop takes when a player opens the file and gives back when that player really closes, so `Release` and `Close` remove only recordings nobody holds, and a file Windows still has open is reported through `PendingCleanup` instead of being assumed deleted. The recording budget (`Options.RecordingBytes`) is separate from the segment budget: a cut first drops the oldest recording nobody holds and is refused with `ErrNoSpace` when everything left is leased, so room is never made by deleting a file a player is reading. The `lease` scenario shows the rule end to end: with a 5 MiB budget and one leased snapshot, three further cuts each drop an unleased one, the leased file stays valid and still decodes after `Close` removed every segment, and it disappears only after the consumer closed and the lease went back (`testplace/evidence/P16/ownership.md`). `-dvr-recording-bytes` sets that budget (default 256 MiB; 0 means unbounded) and the desktop takes one lease per player instance.

Switching a source to a recording is a transaction in `desktop/replay_swap.go`, not an address change. The cut and its lease happen in one buffer lock (`RecordAndLease`), the replacement player is opened on the drawing thread, and the switch is committed only after that player shows a picture: then the item's player, recording and lease are replaced in one main-thread step, and the old player is closed before its lease goes back. A player that cannot open the file, one that never starts and a switch overtaken by a later one all close the replacement, give its lease back and leave the picture and lease the item already had. The item keeps its own address and Core source throughout; the recording it is showing is recorded next to them, so the window and the logs can say "this is history of source 1" instead of pretending the source moved. Closing a source while a switch is still waiting finishes that replacement once — a `sync.Once` owns its player and lease, so the close and a late rollback cannot both give the same lease back — and a player that was showing a recording keeps its lease until it is really closed, even while it waits paused for another player to take over. A buffer only cuts recordings for the source it was started for, and a source that is not in the scene keeps its replacement hidden, so a background switch never takes the picture. The `swap` scenario covers the six switch paths, fails the run when a lease count or the recording on the stage is wrong, and asserts "no lease open" and "no player open" separately; `swap-two` covers a buffer of another source and a background switch (`testplace/evidence/P16/swap.md`).

Three identities are kept apart and never stand in for one another. `PlayerGeneration` names one player's life inside an item and moves when a switch replaces that player. `SourceMediaEpoch` names one run of the source's media clock: `Buffer.Epoch()` starts at `Options.SourceEpoch` (or 1) and moves forward when the playlist states `EXT-X-DISCONTINUITY`, so a recording cut before the jump keeps the epoch it was cut in. `BufferInstance` names one DVR buffer: `Buffer.Instance()` is fixed when the buffer is created, so two buffers of the same source keep two clocks even though their recordings name the same source. `RecordAndLease` copies the instance and the epoch into the `Recording`, and `Anchor` declares the same three things plus the interval it was measured in. `SourceMediaTime` refuses with `ErrNoAnchor` unless the anchor was measured (`MeasuredAt`), names the recording's source, came from the same buffer instance, is for the same epoch, and states an interval that contains the buffer time being mapped. A replay switch therefore increments only the player generation: the `swap` scenario prints `buffer buf-… epoch 1 -> buf-… epoch 1, generation 1 -> 2` and fails the run when any of the three values moves (`testplace/evidence/P16/epoch.md`).

An anchor is **measured**, never inferred from the source id: `desktop/replay_clock.go` asks ffprobe for the container timestamp of the recording's first frame and pairs it with `Recording.StartBufferTime`, so the interval it explains covers that recording. The measurement runs in the background as soon as the buffer holds a segment and never on the drawing thread. An anchor names **which segment it measured**, not when it was measured: `Buffer.CurrentSegment()` hands out that segment, its epoch and its buffer instance under one lock, so after a discontinuity the measurement follows the new clock; a failure is not cached forever, but the trigger for retrying it is **the buffer storing another segment** (`Buffer.NewestSegment()`), not each poll, and a measurement that succeeded is not repeated as the range grows. When one segment cannot be read twice, the runner measures the newest segment instead and anchors on that segment's own buffer start, so windows before it stay refused rather than extrapolated. Conversion follows `B = R + StartBufferTime`, `C = B` (content time: buffer time, counted from the buffer's first segment) and `E = C − the track's confirmed offset`, while the container mapping `M = Anchor.MediaStart + (B − Anchor.BufferStart)` is only used to place a position inside a file, and refuses instead of extrapolating when the anchor was not measured, names another source or buffer instance, is from before a discontinuity moved the epoch, starts after the window being converted, when no single contiguous range holds the whole window (`Buffer.RangeContaining` decides that under one lock, so a skipped segment inside one epoch ends the range even though the epoch has not moved and one anchor must not bridge it), or when the track has no confirmed offset in the Core timeline — a zero offset is legal, an unconfirmed one is not. `commonReplay` therefore no longer treats buffer time as media time: it converts each source's `Available()` start through that source's measured anchor and derives the end from the window's length, because buffer time and media time run together within one epoch and only the start is a measured sample. In one `swap` run over `hls-vod` the media time at buffer `0s` was `1.466667s`, which is how different the two clocks are; running `dvr` over `live-a` and `live-b` measured container PTS bases about 52 seconds apart and reported "do not overlap", where subtracting buffer times had treated them as the same stretch (`testplace/evidence/P16/anchor.md`). The positive case is two playlists of one event: the second carries the same encoded frames with every container timestamp four seconds later, ffprobe and per-frame hashes confirm both halves of that claim, and because the frames are the same the content offset is zero. The `common` scenario confirms a zero offset on both sources and gets the window `0s..30s`, while the anchors still report container starts 1.47 s and 5.47 s apart. Writing that four-second container gap into a track offset instead shrinks the window to `0s..26s`, which is why the gap never becomes an offset, and dropping the confirmation makes `commonReplay` refuse with `ErrNotAligned` (`testplace/evidence/P16/common.md`). The same run also showed the two clocks are not the same clock: a player seek and `Position()` follow the file's own presentation time from its first frame, while the anchor is measured in the container's timestamps, and on material with a mux delay the two differ by that delay — which is why event time is built on content time and the container mapping only opens files. The shared window is now a candidate intersection on the content clock, but it is still not an authorised seek range: a player position that has settled is not a confirmed frame. The conversion lives in `desktop/replay_clock.go` as a small `mediaClock` measured from the anchor: `Player(container)` subtracts the file's first container timestamp and `Container(player)` adds it back, and `playerWindow` maps a buffered window onto the positions a player can seek to, noting that a file cut at the buffer start opens at `anchor.BufferStart`. Converting two files whose frames are the same but whose timestamps differ by four seconds gives both the window `0s..30s`, so the shift stays in the conversion and never becomes a track offset (`testplace/evidence/P16/clock.md`).


A recording's own timeline is the buffer's clock, which begins at the first segment the buffer stored, so position `p` inside the file is buffer time `StartBufferTime + p`, where `StartBufferTime` is the first frame's buffer time and usually less than one segment before the request. That clock is not the source's media clock: the buffer may have joined a live stream mid-flight, so a recording is only placed on the source clock through an `Anchor` measured for that source instance, and a missing or foreign anchor is refused rather than defaulted to zero. Shared event time then subtracts the confirmed track offset. The `contract` scenario checks this against a source with a burned-in timecode: asking for 3 s produces a file that starts at 2 s, its first frame shows `00:00:02.000`, one second into the file the burned-in clock reads `00:00:03.000`, the time that was asked for, and a second cut leaves the first file intact (`testplace/evidence/P16/contract.md`).

The desktop adapter polls each live source's playlist once a second into such a buffer, independently of the picture: pausing the output does not pause the input, which the P8 runs measure. Two buffered sources agree on a common window by converting each `Available()` range to shared event time with the same offset rule as the timeline and intersecting the results; a source without a known offset makes the answer an error rather than a guess, and a source whose range does not overlap is reported rather than silently dropped.

Putting a recording into a running session works in two shapes. The recording can be registered as a source when the session starts and be shown through the scene, and a source imported while the session runs can be opened and shown too: the player is created on the drawing thread and, once it reports ready, the stage draws it and the position advances. The `replay` scenario measures four ways of opening a recording (registered at startup, hidden then switched to, imported while the session runs, and reopened over an existing card) and all four reach `ready=true` with a picture whose burned-in timecode matches the position; the `sources` scenario imports a file while the session runs and reads `ready=true`, `picture=[track-5]`. The file `Join` writes also plays when it is the only source of a process started for it, which is what `desktop`'s `-replay` mode does.

An earlier conclusion that a card created or reopened while the session runs could not draw a picture is withdrawn. Its cause was an application bug — players were created on a goroutine that does not draw the window, so a live HLS player showed no first picture and stopped at the point of a seek — and creating them on the drawing thread fixes it for the live playlist and for recordings alike. The isolation probe that ran before the fix (`testplace/poc/twowin`) still holds: neither the recording nor the window was the obstacle. The loopback endpoint that was tried first was removed because it made no difference.

Cached segments are only checked structurally: a length that is a multiple of 188 bytes, a sync byte at the start of every packet, and a refusal of content that cannot be read or is not a transport stream. That does not prove every frame decodes, so the accurate description is "a bounded HLS segment cache, contiguous range queries over the cached segments, and recording joins"; playing a joined recording has been verified only on Windows with MyGo as the only source.

### Replay clock contract (P16.3d in progress)

Three time domains are named separately, and none of them may stand in for another:

| Domain | Produced by | Rule |
| --- | --- | --- |
| `ContainerPTS` | ffprobe's container timestamps, mux delay included | Evidence and basis identification; also what turns a file position into a player window (`MediaTime`/`playerWindow`), but never Core media time |
| `ContentTime` (buffer time) | The DVR buffer's own clock, counted from the first segment it stored | This is the media time Core's timeline uses: `commonReplay`, `Recording.EventTime` and `replayEventTime` are all built on it |
| `EventTime` | The Core timeline | `ContentTime` minus the track's **confirmed** offset; zero is legal only when confirmed |

Conversion and refusal:

- `B = R + StartBufferTime` (file position to buffer time), `E = B − the confirmed offset` (event time). The container takes no part in this chain.
- Opening a player is a different conversion: `M = Anchor.MediaStart + (B − Anchor.BufferStart)` (container time), then `playerWindow` turns that into a player window.
- An anchor must be measured (`MeasuredAt` non-zero), name the recording's source, the same buffer instance and the same epoch, and state an interval that covers the position being converted; anything else returns `ErrNoAnchor` instead of extrapolating.
- A position inside a recording is a **file position**, not buffer time; `Recording.EventTime` adds `StartBufferTime` itself, so callers must not add it again. The reverse goes through `replayPosition`.
- Two files with the same content but different container timestamps convert to the same event time (measured: two sources four seconds apart in the container both put content 6s at event 6s). That shift stays in the file-position conversion and never becomes a track offset; giving the second source a four-second `TrackOffset` would falsify what a track offset means in the product.
- A shared window is a candidate intersection: it lies in content time, but `Position()` settling still does not mean the target frame is on screen (steady playback lags by a bounded 35ms in an MP4 and about 720ms in a TS recording), so it only becomes a seekable range under P16.4's authorization contract.

### The replay authorisation contract (P16.4a)

`PlanSeek` in `core/dvr` turns one replay request into an immutable `SeekPlan`: the target event time (private, read through `Event()`), the recording and file position each source would have to open, and the identities the decision was made from (source, buffer instance, epoch, player generation, recording id). Every buffer, anchor and recording must set a non-empty instance: three blanks compare equal yet prove nothing about which buffer produced them. It only decides — it opens no player, changes no scene and moves no lease — so it is provable with unit tests alone.

Every condition is checked separately, and any failure returns an error wrapping `ErrNotAuthorized` that names the source and the condition:

- An offset must state **where it came from** (`Alignment{Basis}`); only `measured`, `manual` and `shared-start` count, while an undefined basis or an empty one does not, not even for a zero offset — two buffers that joined a live stream at different moments both report `ContentTime=0s`, and equal numbers are not evidence of the same frame.
- `event + offset` must not overflow, and the content time must not be negative.
- The target must lie inside the **one contiguous range** the buffer holds; a gap, a skipped segment or an evicted range is refused rather than clamped.
- The anchor must be measured, name the recording's source, the same buffer instance and the same epoch, and state an interval covering the time; **the segment it measured must still be inside the range the buffer holds**, so an evicted measurement stops authorising anything.
- The recording must really cover the target content time (`[StartBufferTime, EndBufferTime)`, the right edge being half-open) and have an identity to open (a non-empty id and path).
- The file position is content time minus `StartBufferTime`, so a file cut mid-buffer starts at 0 instead of at the requested time.
- The plan binds the **player generation**: replacing the player invalidates it even when the source, instance, epoch and recording did not move.

`SeekPlan.Matches` compares again before anything is opened, and it compares the **whole identity snapshot** (source, buffer instance, epoch, player generation, offset and its basis, contiguous range, anchor measurement, recording identity) rather than the projected file position: a re-measured anchor or a replaced player can land on exactly the same position and still not be the same decision. A rebuilt buffer, a moved epoch, another recording, a withdrawn offset or a replaced player makes the old decision stale, and the answer says which source changed. The plan's hops are private and `Hops()` hands out a copy, so a decision cannot be rewritten after it was made. This layer only answers "where may we logically go"; whether a position settles, and whether the target frame is on screen, belong to P16.4b/c and are not pretended here.

### Adapting a live session to that contract (P16.4b-1)

`desktop/replay_seek.go` reads **the session as it stands** into the `SeekSource` values `PlanSeek` needs, and reads it again before commitment. Like the contract itself, it opens no file, cuts no recording, takes no lease and touches no player.

- Every field comes from live state: the recording that was really published, the anchor that was really measured, the offset the timeline holds, the generation of the player. Nothing is defaulted.
- **Where an offset came from, and which buffer clock it was placed against, is recorded as a fact.** Anchoring a source and the ±0.1 s nudge both write `manual`, together with the buffer instance and epoch the player was reading at that moment. `shared-start` stays defined for a check this build does not perform: choosing a source as the reference does not prove that two buffers started on the same content frame, so nothing may claim it. `SetShift` moves a number and proves nothing: an offset with no recorded origin is the first case the adapter refuses, because a zero offset and an unconfirmed one look identical.
- **An origin belongs to one buffer.** Content time counts from the first segment a buffer stored, so a calibration made against one buffer says nothing about a buffer built later for the same source; a re-measured anchor does not help either. The adapter refuses when the recorded instance or epoch differs from the buffer it is reading, and only placing that buffer on the timeline again makes it usable.
- **Only a player showing that buffer's recording can record an identity.** A live player runs beside its DVR buffer, but nothing has shown that the live position is that buffer's content clock, so a placement made while it plays records no identity and cannot authorise a replay; the refusal says the offset was placed on a player that was not reading this buffer's recording. A recording player does read a buffer's clock, but through its own file's zero, which begins `StartBufferTime` into the buffer: the playhead an anchor sets and the target a nudge computes are content positions, so they are translated into file positions before the player is asked to seek, and the placement is recorded against that buffer.
- **A recording is never invented.** A source may hold a buffer, but only a `Recording` that was really cut counts; without one the answer says there is no recording to plan around, instead of filling in an id or cutting a file to satisfy the contract.
- **A snapshot cannot splice two moments.** The instance, epoch and ranges are read under one lock (`Buffer.State()`), then read again and required to match; if they moved, the answer is that the buffer changed while its state was read. The test hook `replaySnapshotHook` sits between the two reads, so a unit test can push in a discontinuity and prove the refusal happens. The session is then asked again: a `runners` entry now pointing at another buffer, or an item whose source or generation changed, is refused as replaced while the state was read — the old buffer would otherwise be perfectly stable and its two readings would agree while describing something the session no longer plays.
- Every failure path only returns an error: the player is still nil, nothing was queued for closing, and the buffer's instance and the item's generation are unchanged. `planReplaySeek` hands each source to `PlanSeek`; `confirmReplaySeek` takes the snapshot again and asks `Matches`, passing core's reason through unchanged.

### Turning a decision into resources (P16.4b-2)

`desktop/replay_txn.go` carries out one authorised decision. It reuses the replay player lifecycle that already existed — `recordAndHold` publishes a recording and takes its lease in one step, `measureRecordingAnchor` measures the file that was really written, `openReplayFile` opens a player — and adds only the transaction around them; there is no second player path.

- **The plan is rebuilt from the files that were cut**, not carried over from the one the transaction started with. Each hop's content time is cut, the new recording is measured, and `PlanSeek` runs again on the cut files; a hop whose position does not match where its file starts ends the transaction before anything is committed. The recording and its lease come out of one call, so a file that exists always has a lease holding it.
- **Nothing is replaced until everything is ready.** Each replacement player is drawn under the picture its source already shows (`stage` asks `pendingSeekPlayer`), because a player that is never drawn never produces its first frame, and the transaction waits for one within the same handover budget the single-source switch uses. Only then is the session re-read (`revalidateSeekTxn`): the item's generation, the runner behind it, the calibration's buffer identity and the rebuilt plan's `Matches` must all still hold.
- **The commit is one drawing-thread step** that swaps recording, lease, anchor and player for every source at once and bumps the generation. Everything it depends on is re-checked **inside that same step, before anything is installed**: if one source turns out to have moved, no source changes at all. Old players are closed and old leases released after the swap, so a viewer never sees an empty stage, and a failure anywhere before the commit closes what it opened, releases the leases it took and leaves the sources exactly as they were.
- **The commit does not land the players on the target frame.** A file cut for the target starts at a segment boundary, so the target may sit a few milliseconds into it; the players are at their file's start and the log says how far the seek step still has to go. Asking them for a position and confirming it is P16.4b-3, and neither step may claim a frame was confirmed.

### Landing the players on the target (P16.4b-3)

`settleSeekTxn` runs inside the same transaction, after every replacement has drawn a picture and before anything is committed. Each player is paused, asked for the target's offset inside its own file (`step.offset`, the plan's hop position, not the start of the file), and polled until it reports that position twice in a row within `seekSettleTolerance` (40 ms) while ready and not buffering. A player that keeps playing is played again from there once it has arrived.

- **A player that never arrives is rolled back like any other failure**: the transaction closes what it opened and releases its leases, so a session is never left on a file that cannot show the requested moment.
- **What the transaction proves is a position, not a picture.** The engine reports where the player was asked to go and has no reliable way to say that the frame at that position is the one on screen; the transaction records the position each player *reported* (with what it asked for and the residual between them) and never claims a confirmed frame. An engine error counts as no arrival, and a player within the 40 ms tolerance has not necessarily moved at all, so the log says `requested`, `reported` and `residual` rather than repeating the request.

### One session, two kinds of replay (P16.4b interleaving)

A single-source switch (`playRecording`) and a multi-source transaction can overlap. They hand the session back rather than sharing it: the transaction checks that it is still the registered transaction inside its commit step, before anything is installed, and the switch checks the item's generation before replacing a player. A switch that was overtaken closes the player it opened and releases its lease exactly once; a transaction that was overtaken installs nothing.

Closing the session aborts an open transaction first, so leases and players go back through the same path a failure takes. The preparing work also checks ownership after it opens a player, and closes that player itself if the session or a newer transaction has taken over; each transaction signals when its work has returned, and closing the session waits for that signal (bounded by `seekShutdownWait`) before it closes the buffers the files were cut from. The scenario `interleave` runs both orders and the closing case in one session and reports on leases and generations (`testplace/evidence/P16/interleave.md`).
### What a replay may say about itself (P16.4c)

`desktop/replay_report.go` keeps one account per transaction, and keeps two things apart that are easy to confuse:

- The **phase** describes the transaction: `preparing`, `committed`, `refused`, `rolled back`. Only `committed` is published as a switch. A rolled back transaction keeps the positions it measured but is never shown as a success, and a refusal carries the reason it was refused.
- The **evidence** describes each source: what it was asked for, what its player reported, and the residual between the two. A settled position is reported as a settled position; `FrameConfirmed` is always false, because the engine reports positions and nothing in this build confirms that the frame at such a position is the frame on screen.

The account is an immutable value held by the session: `lastReport` returns a copy, so a surface cannot turn a rollback into a success by waiting or by editing what it holds, and it never reads the transaction's live bookkeeping.
## Web client

`web/` is one Go package (`package main`) plus three static files. A single process serves the embedded page, exposes one Core session as JSON to that page, and serves the test media under `/media/`. It binds a loopback address only (`-addr` is refused unless it is loopback) and prints an address carrying a token at startup. The token appears once in that bootstrap address, becomes an HttpOnly `SameSite=Strict` cookie, and the page strips it from the address bar; the native host sends it as `X-MuxShift-Token`. `/api/` and `/media/` both require it. A request that changes state must also pass two checks: the body must be JSON, which a plain HTML form cannot send, and `Origin`, when present, must equal the request host, so another page cannot drive the session with the cookie the browser holds. Every request must name a loopback `Host`, so a name that resolves to this machine still cannot reach the session. Responses carry no CORS header. Media is opened through `os.OpenRoot`, so `..`, a symbolic link, or a junction inside `-media-root` cannot escape it, and a scene change applies in full or is rejected in full, leaving the previous scene untouched when a volume is invalid.

The page plays HLS through hls.js (the 1.7.4 light build vendored under `web/vendor/`, Apache-2.0, with its exact source, size, and SHA-256 recorded in `web/vendor/README.md`) on top of Media Source Extensions, and hands MP4 files straight to a media element. `GET /api/session` reports the sources, their tracks, and the current scene; `POST /api/scene` changes the scene through `SetSceneVideo` and `SetSceneAudio`, so the web client shares the Core meaning with the desktop: the picture comes from one source, the sound may come from another, and each level and mute state stands on its own.

The difference from the desktop is stated rather than assumed: the web client does not align sources, keeps no history, can only seek inside what the browser has buffered, and starts a live playlist at the live edge. Browsers allow sound only after the user interacts, so every source starts muted and the first click unmutes the source the scene says is heard. Playback failures surface as hls.js error types or media element error codes, and are never smoothed over.

## Browser extension and native host

`extension/` is a Manifest V3 extension whose permissions are `activeTab`, `scripting`, and `nativeMessaging`; it requests no host permission, so it cannot read any page until the user clicks it. After a click the background script runs one read-only scan in the active tab: it collects `src` and `currentSrc` from `video`, `audio`, and `source` elements plus media-looking resource entries. `blob:` and `mediasource:` addresses belong to the page and are refused with a note that the page holds the segments itself; addresses carrying credentials are refused outright.

When the user confirms one address, the extension calls the native host `com.muxshift.bridge` through `chrome.runtime.sendNativeMessage`, so Native Messaging carries only this control message and no media. The host is the Go program in `extension/host/`; it first requires the caller origin in its first argument to equal the extension ID derived from the fixed `key` in `manifest.json` (`chrome-extension://agacmebmmcbkblmekgdkfcehehccl/`), then reads the `%LOCALAPPDATA%\MuxShift\bridge.json` file the session wrote (address and bridge token, mode 0600) and calls `POST /api/import` with `X-MuxShift-Bridge`. The bridge token is a different value from the page token: one lives only between the local file and the host, the other only reaches the page, so a page holding its own cookie cannot import anything. The log of an imported address keeps its scheme, host, and path only, because a signed address carries its credential in the query. The `allowed_origins` entry and the origin argument are what the browser enforces between an extension and its host; they are not authentication against another local process that starts the host itself — the bridge token it does not have is what stops that process.

The session applies the same strict checks to an imported address: `http(s)` only, a host is required, credentials in the URL are refused, and a duplicate registration is refused. It then uses the same `AddSource` and `AddTrack` calls as any other source, so the extension cannot write the timeline or reach desktop internals. The page re-reads the session every two seconds, so an imported source appears without a reload; a cross-origin address plays under that site's CORS rules because the local service does not proxy it, and protected media is never touched. The extension offers no tab capture: a capture yields a live stream only the browser can decode, while the session takes playable addresses and files, and the popup says so instead of pretending.

## Separation experiment

`tools/separate/` splits one recording into a vocal and a non-vocal WAV file with chunked inference on a UVR MDX-Net ONNX export. It is not part of the playback path: neither client calls it, and there is no user-facing switch. The implementation follows the reference project `ultimatevocalremovergui` (`STFT` and `demix`): 44.1 kHz stereo, a 6144-point Hann window, hop 1024, 3072 kept bins, chunks of `hop * (dim_t - 1)` samples with Hann overlap-add, and the non-vocal stem taken as the mixture minus the vocal stem. The model input and output are both `[1, 4, 3072, 256]`.

Measured on this RTX 4060 Laptop (8 GiB): DirectML needs about 0.26 s per 5.92 s chunk (roughly 7.8x realtime, 6.2 GiB of video memory), plain CPU needs about 5.75 s per chunk (slower than realtime). The 5.92 s figure is the length of one model input chunk, not a measured end-to-end delay: overlap-add scheduling, encoding, buffering and player startup all add to what a listener waits for, none of it is measured, and the chunk length must not be written down as a fixed offset between two sources. On a synthetic sample (TTS commentary plus synthetic crowd noise) the vocal stem correlates 0.99 with the commentary source and the non-vocal stem 0.83 with the crowd source, with a 3e-5 reconstruction error. With real recordings (a LibriVox public-domain reading mixed with Wikimedia public-domain applause for 20 s, applause at 0.8) the vocal stem correlates 0.93 with the reading, the non-vocal stem 0.94 with the applause, and the reconstruction error is 2e-5. Commentary inside a real stadium broadcast is still unverified. The two WAV files are stems of one recording rather than two independent live sources: a real integration has to keep the source, the sample rate, the original timeline and the processing delay together, and a cross-source offset can only come from the content timestamps.

The weights have no confirmed license: the code repository states MIT, the weight repository has no LICENSE file, and the upstream issue asking about it was never answered. The model therefore lives only in the ignored `testplace/models/`, the script requires an explicit `--model` path, and neither the repository nor a release ships any weights.

## Alignment probe experiment

`tools/align/` answers "how far apart are these two recordings?" from the content alone: `match.py` reduces a WAV to 10 ms-hop log-energy envelopes at 16 kHz and cross-correlates them, and `frame_hash.py` samples frames with ffmpeg, shrinks each to a 16x16 grey thumbnail, and averages the correlation per lag. Both report the best candidate, the runner-up, and how far the best stands above the median lag; when that gap is too small they refuse and name the failing test instead of picking the highest peak and calling it aligned.

The read-only proposal of the second stage lives in `core/align` and `desktop/align.go`: `Compare` correlates two 16 kHz, 10 ms-hop RMS envelopes per lag in Go, treats lags within 500 ms of the best as the same peak, and derives a confidence from how far the runner-up stands below it; the overlap that takes part in the comparison is sized from the shorter of the two windows and the chosen lag, and anything below `MinOverlap` (10 s by default) or a quarter of the shorter window is refused outright, so a few frames of accidental correlation cannot become a candidate. The desktop's "Try align" button reads the audio of two selected sources (the desktop cannot obtain decoded PCM, so it decodes the same address with ffmpeg), converts the local match offset with `CoreOffset = (MediaStart_B − MediaStart_A) + LocalMatchOffset`, and shows the proposal, its difference from the current offset, the `matched X of Y` span, or the reason it was refused. The decode runs off the UI thread, so the window keeps drawing; the probe first records both windows, the player generations, the target offset, and the sync group, and compares the finished answer against that snapshot, marking it expired — never merging it into the proposal — if any of them changed. It is **not** wired into playback and it **never** writes the timeline: in the desktop the only thing that moves a playback position is the manual ±0.1 s nudge from P7. That keeps an automatic result from overwriting an offset the user already adjusted, and keeps the tool from answering confidently when the two streams share nothing.

Measured on 180-second readings with `--max-lag 60`: prepared offsets of 2, 15, and 45 seconds are all estimated exactly (the resolution is the 10 ms envelope hop), an inserted 3-second silence is measured as +3 s, and a differently mixed pair as 0 s; a different recording, a looped replay, and a 1.05x speed change are all refused. An audio pair takes about 0.1 s. On the video side the fingerprint finds the right lag on the synthetic test pattern, but that pattern looks similar at every lag, so the confidence rule refuses it; the public-domain match footage download was blocked by HTTP 429, so the video path is implemented but unvalidated. Details and numbers live in `tools/align/README.md`.

## Boundaries

- Support independent sources and multiple synchronization groups; do not hard-code two sources as a Core limit.
- Sources, tracks, synchronization relationships, and output scenes are separate concepts. `core` fixes their shape, the event timeline, HLS metadata reading, and a bounded replay buffer; the desktop application registers several sources in one session, selects picture and sound per scene, adjusts each level, aligns one source against another by hand, keeps a bounded history of a live source, cuts a recording out of it and plays and seeks that recording in the session; the web client plays several sources in a browser and switches picture and sound, and the browser extension hands one page address the user picked into the same session; voice separation exists only as an experiment outside the playback path, and automatic alignment exists only as a read-only probe; capture, mixing, automatic cross-source synchronization, replay windows as authorized seek ranges, and live separation are not implemented.
- Browser session access and media capabilities vary by platform. Web cannot assume access to Edge cookies or arbitrary third-party streams; the client states what it cannot do instead of imitating the desktop.
- Keep the Go Core separate from the MyGo UI lifecycle. The desktop application uses MyGo's native playback; other media engines, audio inference, and transport protocols are undecided, and candidates are not installed dependencies.
- `testplace/` stays untracked; formal documentation records stable, verifiable repository facts.

The entry points for verification, what each check covers, and what only runs in a real window are in the [verification index](VERIFICATION.md). In short: the root module and `desktop/` are two Go modules, each with its own `go test ./...`; the desktop's playback, switching, replay and layout results are not unit-tested but measured by its scenario scripts in a real Windows window; the web client's real playback is checked in a browser (Chromium and Edge were verified; browsers that are not installed are recorded as not run); the native host and the extension bridge are checked by hand in Edge with the extension loaded unpacked; the separation and alignment scripts are not Go modules, and their numbers live in `tools/separate/README.md` and `tools/align/README.md`.
